Day 3 openingMaking it worth trusting

Yesterday you made the flight board run and made it reachable. Today you make it something an airport would actually depend on.

Where we start

Two things you built yesterday would not survive a review. The page content lives inside the container, so it vanishes at every restart and every update. The database password was typed on a command line, where it is in your shell history and in the pod specification, readable by anyone with access to the project. And the database itself keeps its data on a disk that disappears with the pod.

Underneath that, a third problem, quieter and worse: the cluster cannot tell a healthy pod from a broken one. A pod that is running but serving errors keeps receiving traffic, for ever, and nothing in the platform notices.

Chapter 10Configuration and persistent storage

By the end of this chapter you will be able to

  • explain why configuration and credentials must live outside the container image;
  • create config maps and secrets from literals and from files, and read them back;
  • inject them as environment variables or as mounted files, and choose between the two;
  • request persistent storage with a claim, and read the access modes without guessing;
  • choose a storage class deliberately, and say what happens to the data when the claim is deleted;
  • deploy a database as a StatefulSet with a volume per replica, behind a headless service.

10.1 Why configuration does not belong in the image

On day 2 you did two things that felt reasonable and were both wrong. You copied a file into a running container with oc cp, and it disappeared at the next restart. You put a database password on a command line, where it went into your shell history and into the pod specification for anyone in the project to read.

The rule is simple, and it is the same rule for every platform: one image, many environments. The image contains the application. Everything that differs between development, test and production — addresses, feature flags, credentials, page content — is supplied at run time. If you have to rebuild an image to change a hostname, the image is wrong.

ObjectHoldsProtected how
ConfigMapNon-sensitive settings: parameters, whole configuration files, page contentNot at all. Anyone who can read the project can read it.
SecretPasswords, tokens, keys, certificatesBy access control, and by not being displayed in most outputs. Not by encryption.
!
Caution

A Secret is Base64-encoded, not encrypted. Anyone who can read secrets in a project can decode every one of them with a single command. What protects a secret is the permission to read it — which is a level 2 topic — and, optionally, encryption of the cluster's etcd database, which a cluster administrator configures. Choosing Secret over ConfigMap is a statement of intent and a hook for access control; it is not, by itself, protection.

10.2 Creating config maps and secrets

# From literal values [you@laptop ~]$ oc create configmap fids-settings \ --from-literal=REFRESH_SECONDS=30 \ --from-literal=TERMINAL=T2 # From a whole file: the key is the file name, the value is its content [you@laptop ~]$ oc create configmap fids-page --from-file=index.html=./index.html # From a directory: one key per file [you@laptop ~]$ oc create configmap fids-conf --from-file=./conf.d/ # A generic secret [you@laptop ~]$ oc create secret generic fids-db-credentials \ --from-literal=POSTGRESQL_USER=fids \ --from-literal=POSTGRESQL_PASSWORD=fids-training \ --from-literal=POSTGRESQL_DATABASE=flights # A TLS secret, from a certificate and its key [you@laptop ~]$ oc create secret tls fids-tls --cert=./tls.crt --key=./tls.key

Reading them back:

[you@laptop ~]$ oc get configmap fids-settings -o yaml [you@laptop ~]$ oc get secret fids-db-credentials -o jsonpath='{.data.POSTGRESQL_USER}' | base64 --decode; echo fids [you@laptop ~]$ oc extract secret/fids-db-credentials --to /tmp/creds --confirm [you@laptop ~]$ ls /tmp/creds POSTGRESQL_DATABASE POSTGRESQL_PASSWORD POSTGRESQL_USER
*
Tip

oc extract writes one file per key, which is the sane way to edit a secret or a large configuration file. Change the file, then push it back with oc set data secret/<name> --from-file=/tmp/creds/POSTGRESQL_PASSWORD. Editing Base64 by hand in a YAML file is how people end up with a trailing newline inside a password.

Written as manifests

i
Note

Use stringData when you write a manifest by hand and data when you read one back — the API accepts the first and always returns the second, Base64-encoded. A ConfigMap has data for text and binaryData for anything that is not valid UTF-8, such as a keystore or an image.

10.3 Injecting: variables or files

There are two ways in, and the choice has real consequences.

MethodThe application seesUpdated when the source changes?
Environment variablesVariables in its process environmentNo. The pod must be restarted.
Mounted volumeOne file per key, in a directoryYes, eventually — the kubelet refreshes the files. But the application must re-read them, which most do not.

As environment variables

Injecting one value, and then all of them
apiVersion: v1
kind: Pod
metadata:
  name: fids-api
spec:
  containers:
    - name: api
      image: registry.access.redhat.com/ubi9/python-311:latest
      env:
        - name: TERMINAL                    # one key, renamed
          valueFrom:
            configMapKeyRef:
              name: fids-settings
              key: TERMINAL
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: fids-db-credentials
              key: POSTGRESQL_PASSWORD
      envFrom:
        - configMapRef:                     # every key, as-is
            name: fids-settings

The same thing, imperatively, on an existing deployment:

[you@laptop ~]$ oc set env deployment/fids-api --from configmap/fids-settings [you@laptop ~]$ oc set env deployment/fids-db --from secret/fids-db-credentials [you@laptop ~]$ oc set env deployment/fids-api --list

As mounted files

[you@laptop ~]$ oc set volume deployment/fids-web --add \ --type configmap --configmap-name fids-page \ --mount-path /var/www/html --name page [you@laptop ~]$ oc set volume deployment/fids-web # list the volumes

Kubernetes creates one file per key in the mount path, named for the key, containing the value. Mounting a config map over a directory replaces what was there in the image — which is exactly what you want for a web root, and exactly what you must not do to /etc.

!
Important

Changing a config map or a secret does not restart the pods that consume it. If the values arrive as environment variables, nothing at all happens until you restart:

[you@laptop ~]$ oc rollout restart deployment/fids-api

This is the single most common “I changed the config and nothing happened” on Kubernetes.

10.4 Lab 10.1 — Real flight data on the board

Guided lab Lab 10.1 — Config maps and secrets
Goal. Put the board content in a config map and the database credentials in a secret, and see what survives a restart. Time. 25 minutes. Prerequisites. The ${U}-platform project from day 2.

  1. Write the page, then make a config map of it:

    [you@laptop ~]$ oc project ${U}-platform [you@laptop ~]$ mkdir -p ~/do108/day3 && cd ~/do108/day3 [you@laptop ~]$ cat > index.html <<'PAGE' <!doctype html> <html><head><title>NCE - Departures</title></head> <body><h1>Nice Cote d'Azur - Departures - Terminal 2</h1> <p>AF7701 08:15 Paris CDG - Boarding</p> <p>BA2633 09:40 London LGW - On time</p> </body></html> PAGE [you@laptop ~]$ oc create configmap fids-page --from-file=index.html=./index.html [you@laptop ~]$ oc get configmap fids-page -o yaml | head -20

  2. Mount it over the web root:

    The real departures page. Note that setting the volume triggered a rollout — the pod template changed, so new pods were created.

  3. Now prove that it survives. This is the whole point of the chapter:

    [you@laptop ~]$ oc delete pod -l app=fids-web [you@laptop ~]$ sleep 20 && curl -s http://$FIDS/ | head -3

    Still there. On day 2 the same test lost the page, because the content lived in the container. Now it lives in the cluster, and the container is disposable again.

  4. Change the content without touching the application:

    [you@laptop ~]$ sed -i 's/Boarding/Final call/' ~/do108/day3/index.html [you@laptop ~]$ oc set data configmap/fids-page --from-file=index.html=~/do108/day3/index.html [you@laptop ~]$ sleep 60 && curl -s http://$FIDS/ | grep -i call
    i
    Note

    Mounted files are refreshed by the kubelet, but not instantly — allow up to about a minute. If you cannot wait, or if the application caches its configuration, oc rollout restart deployment/fids-web is the reliable answer.

  5. Create the database credentials as a secret — never again on a command line:

    [you@laptop ~]$ oc create secret generic fids-db-credentials \ --from-literal=POSTGRESQL_USER=fids \ --from-literal=POSTGRESQL_PASSWORD=fids-training \ --from-literal=POSTGRESQL_DATABASE=flights [you@laptop ~]$ oc get secret fids-db-credentials NAME TYPE DATA AGE fids-db-credentials Opaque 3 5s

  6. See how little a secret protects, so that you never over-trust one:

    [you@laptop ~]$ oc get secret fids-db-credentials -o jsonpath='{.data.POSTGRESQL_PASSWORD}' | base64 --decode; echo fids-training

    One command, no privilege beyond reading the project. Encoding is not encryption.

  7. Deploy the database using the secret:

    [you@laptop ~]$ oc create deployment fids-db --image=quay.io/sclorg/postgresql-15-c9s:latest [you@laptop ~]$ oc set env deployment/fids-db --from secret/fids-db-credentials [you@laptop ~]$ oc rollout status deployment/fids-db [you@laptop ~]$ oc set env deployment/fids-db --list

    The values are referenced, not copied: the deployment holds a pointer to the secret. Rotating the password means changing the secret and restarting, not editing the deployment.

  8. Prove the database works, then destroy it and see what you lose:

    [you@laptop ~]$ oc exec deployment/fids-db -- psql -U fids -d flights \ -c "CREATE TABLE flight (id int, dest text); INSERT INTO flight VALUES (7701,'CDG');" [you@laptop ~]$ oc exec deployment/fids-db -- psql -U fids -d flights -c "SELECT * FROM flight;" [you@laptop ~]$ oc delete pod -l app=fids-db [you@laptop ~]$ sleep 30 && oc exec deployment/fids-db -- psql -U fids -d flights -c "SELECT * FROM flight;" ERROR: relation "flight" does not exist

    The credentials survived. The data did not. That is the second half of this chapter.

10.5 Storage that survives

A container's file system is ephemeral: it is created when the container starts and destroyed when it stops. Persistent storage is requested, not configured — you say what you need, and the cluster provides it.

ObjectWho creates it
PersistentVolume (PV)
cluster-scoped		The administrator, or a provisioner automatically. It represents a real piece of storage.
PersistentVolumeClaim (PVC)
namespaced		You. It states what you need: a size, an access mode, optionally a class. It never names a technology.
StorageClass
cluster-scoped		The administrator. It describes a kind of storage and knows how to create volumes on demand.

That separation is the point: you ask for “5 GiB, writable by one node” and you never need to know whether it is NFS, iSCSI, an EBS volume or an LVM logical volume. Your manifest works on every cluster.

Access modes

ModeShortMeaning
ReadWriteOnceRWORead-write by one node. Several pods on that node can mount it. The common case, and what most block storage supports.
ReadWriteOncePodRWOPRead-write by exactly one pod in the cluster. The strongest guarantee; recommended for databases where it is available.
ReadOnlyManyROXRead-only by many nodes.
ReadWriteManyRWXRead-write by many nodes. Only shared file storage such as NFS supports it.
!
Caution

Neither RWO nor RWX makes concurrent writing safe. RWO permits two pods on the same node to mount the same volume at once; RWX permits any number anywhere. Kubernetes does not arbitrate: two database instances writing to one volume will corrupt it, exactly as two text editors saving the same file would. Correctness is the application's job, and RWOP is the mode that removes the temptation.

Asking for storage

~/do108/day3/fids-db-pvc.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: fids-db-data
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 2Gi
  # storageClassName: gp3-csi     # name it explicitly in production
[you@laptop ~]$ oc apply -f ~/do108/day3/fids-db-pvc.yaml [you@laptop ~]$ oc get pvc NAME STATUS VOLUME CAPACITY ACCESS MODES STORAGECLASS AGE fids-db-data Bound pvc-3f1a... 2Gi RWO gp3-csi 6s # Attach it to a deployment, mount point included [you@laptop ~]$ oc set volume deployment/fids-db --add \ --name data --type pvc --claim-name fids-db-data \ --mount-path /var/lib/pgsql/data
i
Note

A claim that stays Pending is telling you something specific: nothing available satisfies it. Usually the size is larger than any free volume, the access mode is not supported by the class, or the named class does not exist. oc describe pvc <name> says which.

10.6 Storage classes, and what happens to your data

[you@laptop ~]$ oc get storageclass NAME PROVISIONER RECLAIMPOLICY VOLUMEBINDINGMODE AGE gp3-csi (default) ebs.csi.aws.com Delete WaitForFirstConsumer 41d [you@laptop ~]$ oc describe storageclass gp3-csi

Four fields of a storage class change what happens to you:

FieldConsequence
provisionerWhich driver creates the volumes. Determines the access modes and volume modes you can actually get.
reclaimPolicyDelete: deleting the claim destroys the volume and the data. Retain: the volume survives and an administrator must dispose of it. Delete is the default for CSI drivers when the class says nothing.
volumeBindingModeImmediate creates the volume as soon as the claim exists; WaitForFirstConsumer waits until a pod uses it, so the volume is created where the pod will actually run. The second avoids unschedulable pods in a multi-zone cluster.
allowVolumeExpansionWhether you may grow a claim by editing it. Growing only — no storage class shrinks a volume.
!
Important

Always name the storage class in your manifest. The default class is a cluster-wide setting that an administrator can change without telling you, and a manifest that relies on it will one day bind to a different kind of storage with a different reclaim policy. Naming the class is one line and removes a whole category of surprise.

!
Caution

oc delete pvc against a Delete class destroys the data, permanently, with no confirmation. Deleting the whole project does the same thing to every claim in it. In-use protection delays the deletion while pods are still attached, which reads like the platform refusing — it is not; it is waiting.

10.7 Lab 10.2 — Give the database a home

Guided lab Lab 10.2 — Persistent volumes
Goal. Make the flight database survive the loss of its pod. Time. 25 minutes.

  1. See what the cluster offers:

    [you@laptop ~]$ oc get storageclass

    Write down the name of the default class and its reclaim policy. If there is only one, that is normal for a training cluster; the lab uses it and names it explicitly anyway.

  2. Claim some storage:

    ~/do108/day3/fids-db-pvc.yaml
    apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: fids-db-data
  labels:
    app.kubernetes.io/part-of: fids
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 2Gi
    [you@laptop ~]$ oc apply -f ~/do108/day3/fids-db-pvc.yaml [you@laptop ~]$ oc get pvc [you@laptop ~]$ oc describe pvc fids-db-data | tail -8
    i
    Note

    If the status is Pending with an event mentioning waiting for first consumer, that is not a failure: the class uses WaitForFirstConsumer, and the volume will be created when a pod claims it in the next step.

  3. Attach it to the database:

    [you@laptop ~]$ oc set volume deployment/fids-db --add \ --name data --type pvc --claim-name fids-db-data \ --mount-path /var/lib/pgsql/data [you@laptop ~]$ oc rollout status deployment/fids-db [you@laptop ~]$ oc get pvc

    The claim is now Bound. Look at the deployment to see what the command actually wrote:

    [you@laptop ~]$ oc get deployment fids-db -o yaml | grep -A6 'volumeMounts:\|volumes:'

  4. Write data, then destroy the pod:

    [you@laptop ~]$ oc exec deployment/fids-db -- psql -U fids -d flights \ -c "CREATE TABLE flight (id int, dest text); INSERT INTO flight VALUES (7701,'CDG');" [you@laptop ~]$ oc delete pod -l app=fids-db [you@laptop ~]$ oc rollout status deployment/fids-db [you@laptop ~]$ oc exec deployment/fids-db -- psql -U fids -d flights -c "SELECT * FROM flight;" id | dest ------+------ 7701 | CDG

    The same test that failed at the end of Lab 10.1 now passes. Nothing about the application changed — only where it keeps its files.

  5. Look at the volume from the storage side:

    [you@laptop ~]$ oc get pvc fids-db-data -o jsonpath='{.spec.volumeName}{"\n"}' [you@laptop ~]$ oc exec deployment/fids-db -- df -h /var/lib/pgsql/data

  6. Try to delete the claim while it is in use:

    [you@laptop ~]$ oc delete pvc fids-db-data --timeout=10s [you@laptop ~]$ oc get pvc

    The deletion is accepted but does not complete: in-use protection holds it while a pod is attached. The claim shows Terminating and the data is still there. It will disappear the moment the last pod releases it — which is worth knowing before you type this on a real cluster.

    !
    Caution

    Do not scale fids-db to zero now, or the deletion will complete and take the data with it. If you want to keep the claim, remove the deletion by recreating it after detaching, and note in your own runbook that a queued deletion is invisible in oc get pvc beyond the word Terminating.

10.8 When replicas are not interchangeable

A Deployment assumes its pods are identical and disposable. For a database that is false: replica 0 holds different data from replica 1, and a pod that comes back must come back as itself, with its own volume.

A StatefulSet provides exactly that:

GuaranteeWhat it means in practice
Stable namesPods are fids-db-0, fids-db-1, … and keep those names for ever — not a random suffix.
Stable storageEach pod gets its own claim, created from a template and named <template>-<set>-<n>. A restarted pod is reattached to the same volume.
Ordered startPods start one at a time, in order, each waiting for the previous one to be ready.
Stable DNSWith a headless service, each pod is reachable individually at <pod>.<service>.<project>.svc.cluster.local.

The headless service

A normal Service hides its pods behind one address. A database cluster needs the opposite: to address a specific member. Setting clusterIP: None makes the DNS name resolve to the pod addresses themselves.

~/do108/day3/fids-db-headless.yaml
apiVersion: v1
kind: Service
metadata:
  name: fids-db
  labels:
    app.kubernetes.io/name: fids-db
spec:
  clusterIP: None          # headless: no single virtual IP
  selector:
    app.kubernetes.io/name: fids-db
  ports:
    - name: postgresql
      port: 5432
~/do108/day3/fids-db-statefulset.yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: fids-db
spec:
  serviceName: fids-db            # the headless service, which must exist first
  replicas: 2
  selector:
    matchLabels:
      app.kubernetes.io/name: fids-db
  template:
    metadata:
      labels:
        app.kubernetes.io/name: fids-db
        app.kubernetes.io/part-of: fids
    spec:
      containers:
        - name: postgresql
          image: quay.io/sclorg/postgresql-15-c9s:latest
          ports:
            - containerPort: 5432
              name: postgresql
          envFrom:
            - secretRef:
                name: fids-db-credentials
          volumeMounts:
            - name: data
              mountPath: /var/lib/pgsql/data
  volumeClaimTemplates:           # one claim per pod, created automatically
    - metadata:
        name: data
      spec:
        accessModes:
          - ReadWriteOnce
        resources:
          requests:
            storage: 2Gi
i
Note

StatefulSets can only be created from a manifest — there is no oc create statefulset. And oc delete statefulset deliberately leaves the claims behind, so that deleting the workload does not destroy the data. Cleaning up means deleting the claims as a separate, conscious act.

!
Important

A StatefulSet gives each replica its own storage and its own identity. It does not replicate your data between them — that is the database's job, configured inside the application. Two PostgreSQL pods in a StatefulSet are two independent databases until you configure replication, which is beyond the scope of this course.

10.9 Lab 10.3 — The database as a StatefulSet

Guided lab Lab 10.3 — Identity and per-pod storage
Goal. Replace the database Deployment with a StatefulSet, and observe stable names, per-pod volumes and individually addressable pods. Time. 25 minutes.

  1. Remove the Deployment version, keeping the secret:

    [you@laptop ~]$ oc delete deployment fids-db [you@laptop ~]$ oc get pvc

  2. Create the headless service first — the StatefulSet refuses to work without it:

    [you@laptop ~]$ oc apply -f ~/do108/day3/fids-db-headless.yaml [you@laptop ~]$ oc get service fids-db NAME TYPE CLUSTER-IP EXTERNAL-IP PORT(S) AGE fids-db ClusterIP None <none> 5432/TCP 4s

    CLUSTER-IP: None is the headless marker.

  3. Create the StatefulSet and watch the pods start in order:

    [you@laptop ~]$ oc apply -f ~/do108/day3/fids-db-statefulset.yaml [you@laptop ~]$ oc get pods -w NAME READY STATUS RESTARTS AGE fids-db-0 1/1 Running 0 22s fids-db-1 0/1 Pending 0 1s

    Predictable names, and fids-db-1 does not start until fids-db-0 is ready.

  4. Look at the claims that were created for you:

    [you@laptop ~]$ oc get pvc NAME STATUS VOLUME CAPACITY ACCESS MODES data-fids-db-0 Bound pvc-6c2e... 2Gi RWO data-fids-db-1 Bound pvc-91af... 2Gi RWO

    One per pod, named <template>-<set>-<ordinal>. You wrote one template and got two independent volumes.

  5. Prove that the two replicas are genuinely separate:

    [you@laptop ~]$ oc exec fids-db-0 -- psql -U fids -d flights \ -c "CREATE TABLE flight (id int); INSERT INTO flight VALUES (7701);" [you@laptop ~]$ oc exec fids-db-1 -- psql -U fids -d flights -c "SELECT * FROM flight;" ERROR: relation "flight" does not exist

    Two databases, two volumes, no replication. That is the Important box of §10.8, demonstrated.

  6. Address one pod specifically, which is what a headless service is for:

    [you@laptop ~]$ oc run dnscheck --rm -it --restart=Never \ --image=registry.access.redhat.com/ubi9/ubi-minimal:latest -- /bin/sh sh-5.1$ getent hosts fids-db # every pod sh-5.1$ getent hosts fids-db-0.fids-db # exactly one pod sh-5.1$ exit

  7. Destroy a pod and confirm it comes back as itself:

    [you@laptop ~]$ oc delete pod fids-db-0 [you@laptop ~]$ oc get pods -w [you@laptop ~]$ oc exec fids-db-0 -- psql -U fids -d flights -c "SELECT * FROM flight;"

    Same name, same volume, same data. A Deployment could not promise any of the three.

  8. Scale up, then down, and watch the claims:

    [you@laptop ~]$ oc scale statefulset/fids-db --replicas=3 [you@laptop ~]$ oc get pvc [you@laptop ~]$ oc scale statefulset/fids-db --replicas=2 [you@laptop ~]$ oc get pods,pvc

    Scaling down removed the pod and kept the claim. Scale back up and fids-db-2 finds its old data waiting. This is deliberate, and it is also how a project quietly fills up with orphaned volumes.

Check

You can state three things a StatefulSet guarantees that a Deployment does not, show the per-pod claims, resolve one specific pod by DNS name, and explain why fids-db-1 could not see fids-db-0's table.

Summary

  • One image, many environments: settings and credentials are supplied at run time, never baked in.
  • ConfigMaps hold settings and files; Secrets hold credentials and are encoded, not encrypted.
  • Injected as environment variables, values need a pod restart; mounted as files, they refresh on their own but the application must re-read them.
  • Persistent storage is requested through a claim that states size and access mode and never names a technology.
  • Access modes describe who may mount, not who may safely write; correctness stays the application's responsibility.
  • The storage class decides how the volume is created and whether deleting the claim destroys the data — name it explicitly.
  • StatefulSets give stable names, ordered start-up and one volume per replica, and leave the claims behind when deleted; they do not replicate data.

11.1 What the platform expects of an application

Kubernetes keeps applications running. It cannot do that for an application that does not co-operate. Five behaviours are expected, and every one of them is the application's responsibility, not the platform's:

The application mustOtherwise
Tolerate being restarted, at any moment, without warningEvery recovery mechanism the platform has is a restart. An application that needs a graceful, coordinated shutdown to stay consistent cannot be made highly available by the cluster.
Answer health probesThe cluster cannot tell a working pod from a wedged one, and keeps sending traffic to both.
Run as several instances at onceScaling is impossible, and so is a rolling update without an outage.
Use a predictable amount of CPU and memoryThe scheduler has nothing to reason with, and one application can starve every other on the node.
Run without privilegesIt will not start — chapter 8.
!
Important

A crashed pod is not the hard case. A crashed pod is replaced automatically, and you may never notice. The hard case is the pod that is running and not working: a thread pool exhausted, a deadlock, a lost database connection it never retries. Without probes, that pod stays in the Service's endpoint list and keeps receiving requests for as long as it stays alive. Everything in §11.2 exists for that pod.

11.2 Health probes

Three probes, three different questions, three different consequences.

ProbeQuestionConsequence of failure
startupHas it finished starting?The pod is restarted. While it runs, the other two probes are suspended — which is exactly why it exists.
readinessCan it take traffic right now?The pod's address is removed from the Service. The pod keeps running, and is put back when it recovers.
livenessIs it still alive at all?The container is restarted, according to the restart policy.
*
Tip

The distinction that matters in practice: readiness removes traffic, liveness kills the container. If you are not sure which you want, you almost always want readiness first. A liveness probe that is too aggressive turns a slow moment into a restart loop, and a restart loop into an outage.

Three ways to test

TypeSucceeds whenUse for
httpGetThe response code is 200–399Anything that speaks HTTP. The usual choice.
execThe command exits 0Databases and non-HTTP services — for example pg_isready.
tcpSocketThe connection is acceptedA last resort: it proves a port is open, not that the application works.

apiVersion: apps/v1

              path: /
              port: 8080

Timings, and the arithmetic nobody does

FieldMeaning
periodSecondsHow often the probe runs.
failureThresholdHow many consecutive failures before the probe is considered failed.
timeoutSecondsHow long to wait for an answer. The default is 1 second, which is short for a busy application.
initialDelaySecondsHow long to wait before the first check. A startup probe is usually a better answer than a long delay.

Multiply the two first fields and you get the real detection time. periodSeconds: 10 with failureThreshold: 3 means a broken pod keeps taking traffic for up to thirty seconds. That may be fine, or it may be your entire error budget — but it should be a decision, not an accident.

!
Caution

A health endpoint must be cheap. The cluster calls it on every pod, every few seconds, for ever. An endpoint that queries the database on each call turns your health check into a load generator, and makes a slow database look like a fleet of dead pods — which the liveness probe then restarts, one after another.

11.4 Requests: telling the scheduler what you need

When you create a pod, the scheduler filters the nodes that could take it, scores those that remain, and picks the best. The filtering step uses requests: the minimum CPU and memory the pod says it needs.

Requests and limits, in the pod template
apiVersion: apps/v1
kind: Deployment
metadata:
  name: fids-web
spec:
  template:
    spec:
      containers:
        - name: httpd-24
          image: registry.access.redhat.com/ubi9/httpd-24:latest
          resources:
            requests:              # what the scheduler reserves
              cpu: 100m
              memory: 128Mi
            limits:                # what the container may never exceed
              cpu: 500m
              memory: 512Mi
UnitMeaning
1000mOne full CPU core. 100m is a tenth of a core; 0.5 and 500m are the same thing.
128Mi128 mebibytes (220 bytes). 128M is 128 megabytes (106) — not the same, and the difference has caused real incidents.
!
Important

A request reserves capacity; it does not cap consumption. A container requesting 128Mi can use two gigabytes if the node has them. The request is a promise the scheduler makes to you; the limit is a promise you make to everyone else. A pod with no requests is scheduled anywhere, at random, and is the first to be evicted when a node runs short.

# The command that avoids YAML indentation mistakes [you@laptop ~]$ oc set resources deployment/fids-web \ --requests cpu=100m,memory=128Mi --limits cpu=500m,memory=512Mi # What is actually set [you@laptop ~]$ oc get deployment fids-web -o jsonpath=\ '{.spec.template.spec.containers[0].resources}{"\n"}' # Why a pod will not schedule [you@laptop ~]$ oc describe pod <pod> | grep -A5 Events Warning FailedScheduling 0/3 nodes are available: 3 Insufficient memory.

11.5 Limits: protecting everyone else

Limits are enforced by the Linux kernel, through control groups — and the two resources behave completely differently.

ResourceAt the limitEvidence
MemoryThe kernel's OOM killer kills a process. The container is then restarted by the restart policy.reason: OOMKilled and exitCode: 137 in status.containerStatuses[].lastState.terminated, and a growing RESTARTS count.
CPUThe container is throttled. Nothing is killed; everything gets slower, even if the node is idle.No event, no restart, no log line. Only latency — which makes it the harder one to diagnose.
*
Tip

A memory limit is the correct mitigation for a leaking application: it caps the blast radius and turns an unbounded leak into a periodic restart, which buys time while the leak is fixed. A CPU limit is different — set it when you need consistent behaviour across clusters whose nodes differ, and be aware that you are choosing predictable slowness over opportunistic speed.

What the cluster shows you

# Per-node requests and limits, in aggregate (cluster-admin) [admin@laptop ~]$ oc describe node <node> | sed -n '/Allocated resources/,/Events/p' # Real usage, not reservations (cluster-admin) [admin@laptop ~]$ oc adm top pods -n user1-platform [admin@laptop ~]$ oc adm top nodes
i
Note

oc describe node prints “Total limits may be over 100 percent, i.e. overcommitted”. That is normal and intended: a node can promise more limit than it owns, because not every container peaks at once. It may never overcommit requests — those are reservations, and that is why a pod requesting more than any node can offer stays Pending for ever.

11.7 Horizontal pod autoscaling

A HorizontalPodAutoscaler changes the replica count of a Deployment or a StatefulSet according to a measured metric — usually CPU. It is a control loop in the controller manager, checking roughly every fifteen seconds.

StepWhat the loop does
1Read the target from the HPA — for example, 60 % CPU.
2Collect the current usage of every targeted pod from the metrics server.
3Express each pod's usage as a percentage of its CPU request.
4Average across pods, compare with the target, and compute a new replica count.
5Scale, within the configured minimum and maximum.
!
Important

Step 3 is why an autoscaler cannot work without resource requests. “Sixty per cent” means sixty per cent of the request; with no request there is nothing to take a percentage of. A deployment created with oc create deployment has no requests, so its HPA shows <unknown> in the TARGETS column and never scales. That symptom is almost always this cause.

# Imperatively [you@laptop ~]$ oc autoscale deployment/fids-web --min=2 --max=6 --cpu-percent=60 [you@laptop ~]$ oc get hpa NAME REFERENCE TARGETS MINPODS MAXPODS REPLICAS fids-web Deployment/fids-web 4%/60% 2 6 2
~/do108/day3/fids-web-hpa.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: fids-web
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: fids-web
  minReplicas: 2
  maxReplicas: 6
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60
i
Note

A brand-new HPA shows <unknown> for a few minutes while metrics accumulate; that is normal. <unknown> that never resolves is the missing-request problem above. oc describe hpa says so explicitly, in its ScalingActive condition.

*
Tip

Autoscaling on memory is possible and rarely useful. Most runtimes — the JVM especially — claim memory at start-up and never give it back, so memory usage does not track load. If the metric does not move with the traffic, the autoscaler cannot help.

11.10 Watch out, and summary

Watch out

TrapWhat is really happening
A liveness probe on the wrong port or pathEvery pod restarts for ever. The most common self-inflicted outage there is. Add readiness first, liveness later.
A liveness probe with no startup probe on a slow applicationThe pod is killed before it has finished starting, and never starts at all.
An expensive health endpointThe probes become a load generator, and a slow dependency turns into a fleet-wide restart.
periodSeconds × failureThreshold never computedA broken pod serves errors for thirty seconds because nobody multiplied 10 by 3.
No requestsRandom placement, first to be evicted, and no autoscaling — ever.
Requests set to average usageThe node is overcommitted and evicts pods under load. Size requests for the peak.
128M where you meant 128MiA 7 % shortfall, which is enough to cause an OOM kill at exactly the wrong moment.
Raising a limit to stop an OOMKilledSometimes correct, often a leak being hidden. Decide which, and write it down.
HPA stuck at <unknown>No CPU request on the target. oc describe hpa says so.

Summary

  • High availability is a contract: the application must tolerate restarts, answer probes, run in several copies, behave predictably and run unprivileged.
  • Readiness removes a pod from the Service; liveness restarts the container; a startup probe protects a slow start from both.
  • Detection time is periodSeconds × failureThreshold — compute it on purpose.
  • Requests are reservations that drive scheduling; limits are caps enforced by the kernel.
  • Exceeding a memory limit kills the process (OOMKilled, exit 137); exceeding a CPU limit throttles it silently.
  • An HPA measures usage as a percentage of the request, so without requests it can never work.
  • Set a maximum on every autoscaler: it is what protects the rest of the cluster from your application.

Three questions to check yourself

Answer without looking back, then check

  1. You update a ConfigMap that a deployment consumes as environment variables. What happens to the running pods, and what do you do about it? Nothing happens: environment variables are read once, at container start. oc rollout restart deployment/<name>. Mounted files are different — they refresh, slowly, and only help if the application re-reads them.
  2. A pod shows RESTARTS 7 and its logs are empty. Which single command settles it, and what are you looking for? oc get pod <p> -o jsonpath='{.status.containerStatuses[0].lastState.terminated}' — looking for reason: OOMKilled and exitCode: 137. The logs are empty because the kernel killed the process without warning it.
  3. Your HPA has shown <unknown> for twenty minutes. What is wrong, and where does the cluster tell you? The target has no CPU request, so utilisation cannot be computed. oc describe hpa <name> shows ScalingActive False FailedGetResourceMetric … missing request for cpu.
