Chapter 8Running applications as containers and pods

By the end of this chapter you will be able to

  • start a single pod by hand, and say why you should almost never do it in production;
  • explain which user ID your container actually runs as on OpenShift, and why so many images fail;
  • identify a container image precisely: registry, name, tag, digest;
  • read an image's runtime metadata before deploying it - command, user, ports, environment;
  • diagnose a pod that will not start, using events, logs, a shell and a tunnel;
  • choose the right troubleshooting tool for the symptom in front of you.

8.1 One pod, started by hand

oc run creates a single pod, directly. No Deployment, no ReplicaSet, nothing watching it. If its node fails it is gone; if the process exits it is not replaced. That is not a defect - it is the point. A bare pod is the right tool for two jobs, and only two: a temporary task, and debugging.

# The simplest possible pod: run a command, keep the output, stop [you@laptop ~]$ oc run show-date --image=registry.access.redhat.com/ubi9/ubi-minimal:latest \ --restart=Never -- date pod/show-date created [you@laptop ~]$ oc logs show-date Mon Sep 8 09:41:07 UTC 2026
OptionWhat it does
-- <args>Passes arguments to the image's own entry point.
--command -- <cmd>Replaces the image's command entirely. The difference matters: without --command, your words are arguments; with it, they are the program.
-itKeeps stdin open and allocates a terminal - an interactive shell in the container.
--restart=Always|OnFailure|NeverThe pod's restart policy. Always is the default and is wrong for a task that is supposed to finish.
--rmDeletes the pod when it exits. Use it with -it so you do not leave debris behind.
--env K=VSets an environment variable. Repeat for several.
--dry-run=client -o yamlPrints the manifest instead of creating anything - the fastest way to get a correct skeleton to edit.
*
Tip

--dry-run=client -o yaml is worth more than it looks. Rather than writing a pod manifest from memory, generate it and edit it:

[you@laptop ~]$ oc run fids-web --image=registry.access.redhat.com/ubi9/httpd-24:latest \ --port=8080 --dry-run=client -o yaml > fids-web-pod.yaml

The same trick works with oc create deployment, oc create job and most other imperative commands. It is how experienced people write correct YAML quickly.

Restart policies, and the mistake they cause

PolicyBehaviourUse it for
AlwaysRestart the container whatever the exit code - including exit 0.Servers. The default.
OnFailureRestart only on a non-zero exit code.A task that should be retried until it succeeds.
NeverDo not restart. The pod ends as Succeeded or Failed.A one-shot task whose output you want to read.
!
Caution

Running a finite command with the default Always policy produces a pod that succeeds, is restarted, succeeds again, and eventually shows CrashLoopBackOff - for a program that works perfectly. If you see CrashLoopBackOff on a command that is supposed to end, look at the restart policy before you look at the application.

8.2 Who your container actually runs as

This section explains the single most common reason a container that works on a laptop fails on OpenShift. It is worth reading twice.

A container image can declare the user it wants to run as, with the USER instruction. On a plain container engine, that is honoured. On OpenShift, for a regular user, it is ignored: the platform assigns an arbitrary user ID taken from a range allocated to your project, and sets the primary group to 0 - the root group, which is not the root user.

[you@laptop ~]$ oc describe project ${U}-fids | grep sa.scc openshift.io/sa.scc.uid-range=1000750000/10000 openshift.io/sa.scc.supplemental-groups=1000750000/10000 openshift.io/sa.scc.mcs=s0:c26,c25 [you@laptop ~]$ oc run whoami --image=registry.access.redhat.com/ubi9/ubi-minimal:latest \ --restart=Never --rm -it -- id uid=1000750001 gid=0(root) groups=0(root),1000750001

The annotation reads base/size: ten thousand identifiers starting at 1000750000, reserved for this project. Every project gets a different block, so a file written by one project's container can never be mistaken for another's.

Why it is done this way, and what it breaks

The ruleThe consequence for images
The container does not run as rootAnything that needs to write to /etc, install packages, or bind a port below 1024 fails. Web servers that expect port 80 are the classic case.
The user ID is unpredictableAn image that creates /data owned by UID 1001 and writes to it as UID 1001 fails, because the container is not 1001.
The primary group is always 0This is the escape hatch. A directory owned by root group with group write permission (drwxrwx--- root root) is writable by any assigned UID. Well-built images do exactly that.
!
Important

When an image fails with Permission denied on OpenShift and works with podman run on your laptop, this is almost always why. The correct fix is to use an image built for arbitrary user IDs - Red Hat's UBI and database images are - not to grant the container more privileges. Granting privileges is possible, requires a cluster administrator, and is covered in the level 2 course.

i
Note

A second mechanism, Pod Security Admission, checks pods against a privileged, baseline or restricted profile applied to the namespace. In this course you will occasionally see a warning about it when you create a pod with no security context. The warning is informational; the pod runs.

8.3 Lab 8.1 - The flight board as a bare pod

Guided lab Lab 8.1 - One pod, by hand
Goal. Start, inspect and stop an unmanaged pod, and see the user ID OpenShift gave it. Time. 20 minutes.

  1. Create the day's project and read its identifier range:

    [you@laptop ~]$ oc new-project ${U}-pods [you@laptop ~]$ oc describe project ${U}-pods | grep sa.scc

    Write the base value down. Every container you run in this project gets an ID in that block.

  2. Run a one-shot task and read its output:

    [you@laptop ~]$ oc run board-check --restart=Never \ --image=registry.access.redhat.com/ubi9/ubi-minimal:latest -- date [you@laptop ~]$ oc get pods NAME READY STATUS RESTARTS AGE board-check 0/1 Completed 0 8s [you@laptop ~]$ oc logs board-check

    Completed, not Running. The container did its job and exited, and because the policy is Never, nothing restarted it.

  3. Do the same thing wrong, on purpose, and watch what happens:

    [you@laptop ~]$ oc run board-loop \ --image=registry.access.redhat.com/ubi9/ubi-minimal:latest -- date [you@laptop ~]$ oc get pods -w

    Wait a minute. The pod cycles Completed → Running → CrashLoopBackOff, for a command that never failed. The default restart policy is Always. Press Ctrl-C, then remove it:

    [you@laptop ~]$ oc delete pod board-loop board-check

  4. Run the actual flight board, as a long-lived pod:

    [you@laptop ~]$ oc run fids-web --image=registry.access.redhat.com/ubi9/httpd-24:latest --port=8080 [you@laptop ~]$ oc get pods -o wide

  5. Find out who it is.

    [you@laptop ~]$ oc exec fids-web -- id uid=1000750001 gid=0(root) groups=0(root),1000750001 [you@laptop ~]$ oc exec fids-web -- whoami whoami: cannot find name for user ID 1000750001

    whoami fails because that user ID has no entry in the image's /etc/passwd. The container runs perfectly anyway. This surprises applications that call getpwuid() - another reason to prefer images designed for OpenShift.

  6. Prove that it cannot write where root could:

    [you@laptop ~]$ oc exec fids-web -- sh -c 'echo test > /etc/motd' sh: /etc/motd: Permission denied command terminated with exit code 1 [you@laptop ~]$ oc exec fids-web -- sh -c 'ls -ld /tmp && touch /tmp/ok && echo written' drwxrwxrwt. 1 root root 6 ... /tmp written

    That is the whole lesson of §8.2, in two commands.

  7. Open an interactive shell, look around, and leave:

    [you@laptop ~]$ oc exec -it fids-web -- /bin/bash bash-5.1$ ls -ld /var/www/html bash-5.1$ cat /etc/redhat-release bash-5.1$ exit

    Note the permissions on /var/www/html: root-owned, root group, group-writable. That is an image built for arbitrary user IDs.

  8. Reach the application without a Service or a Route, using a local tunnel:

    [you@laptop ~]$ oc port-forward pod/fids-web 8080:8080 Forwarding from 127.0.0.1:8080 -> 8080

    In a second terminal:

    [you@laptop ~]$ curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/ 200

    Stop the tunnel with Ctrl-C. This is a diagnostic tool, not a way to publish an application: it exists only in your terminal, for you.

  9. Delete the pod and watch nothing happen.

    [you@laptop ~]$ oc delete pod fids-web [you@laptop ~]$ oc get pods No resources found in user1-pods namespace.

    Nothing replaced it, because nothing was watching it. Chapter 9 fixes exactly that.

?
Check

You can explain: why a finite command ends in CrashLoopBackOff with the default policy; what UID your container ran as and where that number came from; why /etc/motd was refused and /tmp was not; and why deleting the pod left you with nothing.

8.4 Knowing exactly which image you are running

An image reference has four parts, and only three of them are usually written:

Anatomy of an image reference
registry.access.redhat.com / ubi9/httpd-24 : 1-266
└─── registry ────────────┘ └─ name ──────┘ └ tag ┘

registry.access.redhat.com/ubi9/httpd-24@sha256:9f2a...c41b
                                        └──── digest ─────┘
PartWhat it is
RegistryWhere the image lives. Omitted, it defaults to a registry configured on the cluster - so always write it.
NameThe repository path inside the registry.
TagA human-friendly label. It can be moved. Omitted, it defaults to latest.
DigestThe SHA-256 of the image content. It cannot be moved. A digest identifies exactly one image, for ever.

Floating tags and fixed tags

A floating tag - latest, 1, 8.0 - points at whatever the publisher considers current. A fixed tag - 1-266 - points at one build. Several tags can point at the same image; the digest is what tells you they do.

!
Caution

An application deployed with :latest can change under you, silently, at the next pod restart - on a different node, at three in the morning, with nobody having deployed anything. Every lab in this book uses :latest for convenience and says so; chapter 12 shows what to do instead, and it is not optional.

Reading an image before you run it

oc image info is part of the client you already have. No daemon, no root, no extra installation:

[you@laptop ~]$ oc image info registry.access.redhat.com/ubi9/httpd-24:latest \ --filter-by-os linux/amd64 Name: registry.access.redhat.com/ubi9/httpd-24:latest Digest: sha256:9f2a...c41b Media Type: application/vnd.docker.distribution.manifest.v2+json Created: 3w ago Image Size: 259.1MB in 4 layers OS: linux Arch: amd64 Entrypoint: container-entrypoint Command: /usr/bin/run-httpd Working Dir: /opt/app-root/src User: 1001 Exposes Ports: 8080/tcp, 8443/tcp Environment: HTTPD_VERSION=2.4 APP_ROOT=/opt/app-root ... Labels: name=ubi9/httpd-24 release=... version=1
i
Note

--filter-by-os is required for multi-architecture repositories; without it the command reports a manifest list rather than an image. Add it as a habit.

Four of those lines decide whether the image will work for you:

FieldWhat it tells you
Entrypoint / CommandWhat runs when the container starts - and therefore what your --command would replace.
UserThe user the image expects. OpenShift will ignore it, so an image with User: 0 is a warning sign: it was built assuming root.
Exposes PortsDocumentation, nothing more - it opens no port. But it tells you which port the application actually listens on, which is what your Service will need.
EnvironmentThe variables the image reads. Many images refuse to start until some of them are set.

Base images, in one paragraph

Red Hat's Universal Base Images (UBI) are OCI-compliant, redistributable without a subscription, and built to run as an arbitrary user. Four variants exist: standard (with dnf and systemd), init (for running several services), minimal (with microdnf, much smaller), and micro (no package manager at all). Language runtime images - python-311, httpd-24, nodejs-20 - are built on top of them. The labs use minimal for tooling and the runtime images for the applications.

8.5 Lab 8.2 - Inspect before you deploy

Guided lab Lab 8.2 - Reading images
Goal. Decide, from an image's metadata alone, what it needs in order to run - then prove it. Time. 20 minutes.

  1. Inspect the three images of the running example:

    [you@laptop ~]$ oc image info registry.access.redhat.com/ubi9/httpd-24:latest --filter-by-os linux/amd64 [you@laptop ~]$ oc image info registry.access.redhat.com/ubi9/python-311:latest --filter-by-os linux/amd64 [you@laptop ~]$ oc image info quay.io/sclorg/postgresql-15-c9s:latest --filter-by-os linux/amd64

    For each one, write down four things: the digest, the user, the exposed ports, and the environment variables whose names suggest they are required.

  2. Compare a floating tag with a fixed one. Take a versioned tag from the output above and check whether it is the same image:

    [you@laptop ~]$ oc image info registry.access.redhat.com/ubi9/httpd-24:latest \ --filter-by-os linux/amd64 -o json | grep -m1 digest

    Two tags with the same digest are the same image. Two tags with different digests are two different applications wearing similar names.

  3. Run the database without configuring it, and read what it says:

    [you@laptop ~]$ oc run fids-db --image=quay.io/sclorg/postgresql-15-c9s:latest [you@laptop ~]$ oc get pods NAME READY STATUS RESTARTS AGE fids-db 0/1 CrashLoopBackOff 2 55s [you@laptop ~]$ oc logs fids-db You must specify the following environment variables: POSTGRESQL_USER POSTGRESQL_PASSWORD POSTGRESQL_DATABASE

    The image told you exactly what it needs. Most do - the mistake is not reading.

  4. Run it properly:

    [you@laptop ~]$ oc delete pod fids-db [you@laptop ~]$ oc run fids-db --image=quay.io/sclorg/postgresql-15-c9s:latest \ --env POSTGRESQL_USER=fids \ --env POSTGRESQL_PASSWORD=fids-training \ --env POSTGRESQL_DATABASE=flights [you@laptop ~]$ oc get pods -w
    !
    Caution

    A password on a command line ends up in your shell history and in the pod's specification, readable by anyone who can read the project. It is acceptable here because it is a training database with no data. Chapter 10 replaces it with a Secret, which is where credentials belong.

  5. Check that the database really works, from inside its own pod:

    [you@laptop ~]$ oc exec fids-db -- psql -U fids -d flights -c '\l' [you@laptop ~]$ oc exec fids-db -- id

    Note the user ID: it is from your project's range, not the User the image declared.

  6. Reach it from another pod, by IP address, to see why that is a bad idea:

    [you@laptop ~]$ DBIP=$(oc get pod fids-db -o jsonpath='{.status.podIP}') [you@laptop ~]$ echo $DBIP [you@laptop ~]$ oc run dbclient --rm -it --restart=Never \ --image=quay.io/sclorg/postgresql-15-c9s:latest \ \--env PGPASSWORD="fids-training" -- psql -h $DBIP -U fids -d flights -c 'SELECT version();'

    It works. Now delete fids-db and recreate it: the IP changes, and everything that hard-coded it breaks. That problem is what Services exist for, in chapter 9.

  7. Clean up:

    [you@laptop ~]$ oc delete pod fids-db
?
Check

You can state, for any image, how to find: the exact bytes it refers to, the command it will run, the port it listens on, and the environment it requires - before creating a single pod.

8.6 The troubleshooting toolkit

Seven tools. The skill is not knowing them - it is picking the right one from the symptom, in five seconds.

SymptomReach forBecause
Pod is Pendingoc describe podIt never got scheduled. The events say why: no room, no matching node, a quota.
ImagePullBackOffoc describe podThe image name, the tag, or the credentials. The event message is explicit.
CrashLoopBackOffoc logs --previousThe container ran and died. The current container has no output yet; the previous one has the reason.
Running but wrongoc logs -f, then oc rshThe application started and is misbehaving. This is its own account of events, then a look inside.
“Is it even listening?”oc port-forwardA private tunnel from your laptop straight to the pod, bypassing Service, Route and DNS.
Need a file in or outoc cp / oc rsyncCopy a configuration in, or a log out, without rebuilding anything.
The pod has no shell, or will not startoc debugIt starts a modified copy of the pod - probes disabled, command replaced by a shell - so you can look at an image that cannot run.

The commands themselves

# Events: what the cluster did, and where it stopped [you@laptop ~]$ oc describe pod <pod> # events are at the bottom [you@laptop ~]$ oc get events --sort-by .metadata.creationTimestamp # Logs: what the application said [you@laptop ~]$ oc logs <pod> [-c <container>] [you@laptop ~]$ oc logs <pod> --previous # the container that died [you@laptop ~]$ oc logs -f deployment/fids-web --tail=20 [you@laptop ~]$ oc logs -l app.kubernetes.io/part-of=fids # all pods of an app # Inside the container [you@laptop ~]$ oc exec <pod> -- ls -la /var/www/html [you@laptop ~]$ oc rsh <pod> # interactive shell # Files across the boundary [you@laptop ~]$ oc cp ./index.html <pod>:/var/www/html/index.html [you@laptop ~]$ oc cp <pod>:/var/log/app.log ./app.log # A tunnel from your laptop to the pod [you@laptop ~]$ oc port-forward <pod> 8080:8080 # A debuggable copy of a pod that will not start [you@laptop ~]$ oc debug pod/<pod> # Change one field without rewriting the object [you@laptop ~]$ oc edit pod/<pod> [you@laptop ~]$ oc patch pod/<pod> --type='json' \ -p='[{"op":"replace","path":"/spec/containers/0/image","value":"…"}]'
i
Note

oc cp needs the tar binary inside the container and fails without it - which is why it does not work on micro images. In a pod with several containers, cp, exec, rsh and logs all target the first container unless you name one with -c.

!
Caution

Everything you change inside a running container is lost at the next restart, and is invisible to anyone reading your manifests. Editing a live container is a legitimate way to find a fix and never a way to apply one. When it works: write it down, change the source, redeploy.

8.7 Lab 8.3 - Diagnose three broken pods

Guided lab Lab 8.3 - Reading failures
Goal. Meet the three failure modes you will see most often, and fix each with the right tool. Time. 25 minutes.

  1. Failure 1 - a tag that does not exist.

    [you@laptop ~]$ oc run fids-web --image=registry.access.redhat.com/ubi9/httpd-24:2.4-9999 --port=8080 [you@laptop ~]$ oc get pods NAME READY STATUS RESTARTS AGE fids-web 0/1 ImagePullBackOff 0 30s

    Diagnose it. Note that oc logs is useless here - there is no container:

    [you@laptop ~]$ oc logs fids-web Error from server (BadRequest): container "fids-web" in pod "fids-web" is waiting to start: trying and failing to pull image [you@laptop ~]$ oc describe pod fids-web | tail -8

    Fix it in place, then confirm:

    [you@laptop ~]$ oc patch pod/fids-web --type='json' -p='[{"op":"replace","path":"/spec/containers/0/image","value":"registry.access.redhat.com/ubi9/httpd-24:latest"}]' [you@laptop ~]$ oc get pods
    i
    Note

    Patching the image of a live pod works because the image field is one of the very few a pod allows you to change. Almost everything else in a pod is immutable - which is why real applications are managed by a Deployment, and why chapter 9 exists.

  2. Failure 2 - the application dies at startup.

    [you@laptop ~]$ oc run fids-db --image=quay.io/sclorg/postgresql-15-c9s:latest [you@laptop ~]$ oc get pods fids-db -w

    Once it reaches CrashLoopBackOff, read the right log:

    [you@laptop ~]$ oc logs fids-db # may be empty: the container has just restarted [you@laptop ~]$ oc logs fids-db --previous # the one that actually failed

    The message names the three variables it wants. Delete and recreate with them, as in Lab 8.2.

  3. Failure 3 - it runs, but serves the wrong thing. Your flight board is up and showing the container's default page. Fix the content the wrong way, deliberately:

    ~/do108/day2/index.html
    <!doctype html>
<html><head><title>NCE - Departures</title></head>
<body>
<h1>Nice Cote d'Azur - Departures</h1>
<p>AF7701 08:15 Paris CDG - Boarding</p>
<p>BA2633 09:40 London LGW - On time</p>
</body></html>
    [you@laptop ~]$ oc cp ~/do108/day2/index.html fids-web:/var/www/html/index.html [you@laptop ~]$ oc exec fids-web -- ls -la /var/www/html/ [you@laptop ~]$ oc port-forward pod/fids-web 8080:8080 & [you@laptop ~]$ curl -s http://127.0.0.1:8080/ | head -4

    The board now shows real departures. Now prove that this was the wrong fix:

    [you@laptop ~]$ kill %1 # stop the tunnel [you@laptop ~]$ oc delete pod fids-web [you@laptop ~]$ oc run fids-web --image=registry.access.redhat.com/ubi9/httpd-24:latest --port=8080

    The page is gone. Nothing recorded it, nothing reapplies it. Chapter 10 puts that file in a ConfigMap, where it belongs.

  4. Use oc debug on something that cannot run.

    [you@laptop ~]$ oc debug pod/fids-web sh-5.1$ id sh-5.1$ ls -ld /var/www/html /etc sh-5.1$ exit

    oc debug made a copy of the pod with the command replaced by a shell and the probes removed. The original is untouched. This is how you inspect an image whose own process fails immediately.

  5. Clean up the whole day's sandbox:

    [you@laptop ~]$ oc delete pod --all
?
Check

Given only a STATUS value, you can now name the command you would type next - Pending and ImagePullBackOff to describe, CrashLoopBackOff to logs --previous, Running to logs then rsh. That reflex is the deliverable of this chapter.

8.8 Workshop 8.4 - The 06:40 incident

Workshop Workshop 8.4 - On call
Goal. Diagnose and repair without step-by-step instructions. Time. 25 minutes. Rule. Write down, for each incident, the command that told you the answer - that is the deliverable, not the fix.

Setup. Create the incident project and the three broken pods:

[you@laptop ~]$ oc new-project ${U}-incident [you@laptop ~]$ oc run board-a --image=registry.access.redhat.com/ubi9/httpd-24:99 --port=8080 [you@laptop ~]$ oc run board-b --image=quay.io/sclorg/postgresql-15-c9s:latest [you@laptop ~]$ oc run board-c --image=registry.access.redhat.com/ubi9/ubi-minimal:latest -- /bin/false

The call. At 06:40 the duty officer reports that the departure boards in Terminal 2 are blank. You find three pods in the project and none of them is healthy.

  1. For each of the three pods, state which of the six steps of §6.3 it failed at.
  2. For each, give the one command that proves your diagnosis, and quote the line of output that does it.
  3. Repair board-a without deleting it.
  4. Repair board-b. You may delete and recreate it - but explain in one sentence why you had to, when you did not have to for board-a.
  5. board-c cannot be repaired as it stands. Say why in one sentence, and say what you would change if this were a real application.
  6. Serve the real departures page from board-a, and prove it works from your laptop without creating a Service or a Route.
  7. Clean up: oc delete project ${U}-incident.
*
Tip

If you are stuck for more than three minutes on one pod, move to the next and come back. Two of the three are diagnosed by the same command; noticing that is part of the exercise.

?
Check

Your notes should contain three different commands for three different symptoms, and the words describe, --previous and port-forward should each appear once. Compare with your neighbour: if one of you used logs where the other used describe, work out which was right, and why.

8.9 Watch out, and summary

Watch out

TrapWhat is really happening
CrashLoopBackOff on a command that worksRestart policy Always on a finite command. Use --restart=Never.
oc logs returns nothing usefulThe container just restarted. Use --previous.
Permission denied on a file the image createdThe container is not the user the image expected. Use an image built for arbitrary UIDs.
Fixing a container with oc cp or oc rshThe fix disappears at the next restart, and nobody else can see it. Diagnose live; fix in the source.
Hard-coding a pod IP addressPod IPs change on every restart. That is what Services are for - chapter 9.
Deploying with :latestThe image can change without you. Chapter 12.
Treating oc port-forward as publishingIt exists only in your terminal, only for you. Routes publish - chapter 9.

Summary

  • oc run creates an unmanaged pod: nothing reschedules it, nothing replaces it. Use it for temporary tasks and for debugging, never for an application.
  • The restart policy decides what happens when the process ends; Always on a finite command produces a misleading CrashLoopBackOff.
  • OpenShift ignores an image's USER for regular users and assigns an arbitrary UID from the project's range, with primary group 0. Images must be built for that.
  • An image is identified by registry, name, tag and digest; only the digest is immutable.
  • oc image info tells you the command, the user, the ports and the environment an image expects - before you create anything.
  • Match the tool to the symptom: describe for what never started, logs --previous for what died, logs and rsh for what misbehaves, port-forward to test reachability, debug for what cannot run at all.
  • Containers are immutable and ephemeral: diagnose inside them, fix in the source.

9.1 From a bare pod to a managed application

At the end of chapter 8 you deleted a pod and nothing came back. That is the difference this chapter closes. A Deployment is an object that says “I want n pods that look like this”, and a controller makes it true, permanently.

ObjectCreated byResponsibility
DeploymentYouHolds the pod template and the update strategy. This is the object you write, read and change.
ReplicaSetThe DeploymentKeeps exactly n pods matching its selector alive. One per version of the pod template.
PodThe ReplicaSetRuns the containers. Disposable by design.
!
Important

Never edit a ReplicaSet. It is managed on your behalf, and your change will be reverted or will silently break the next rollout. You change the Deployment; the Deployment changes the ReplicaSet. The same rule applies to pods created by a controller.

Three ways to create the same application

# Imperative: fast, unrepeatable, nothing written down [you@laptop ~]$ oc create deployment fids-web --image=registry.access.redhat.com/ubi9/httpd-24:latest # oc new-app: builds several objects at once from an image, a template or a git repository [you@laptop ~]$ oc new-app --image registry.access.redhat.com/ubi9/httpd-24:latest --name fids-web # Declarative: slower to type once, then reproducible for ever [you@laptop ~]$ oc apply -f fids-web-deployment.yaml

Use the first to explore, the second to bootstrap, and the third for anything you intend to keep. The bridge between them is the same option as in chapter 8:

[you@laptop ~]$ oc create deployment fids-web --image=registry.access.redhat.com/ubi9/httpd-24:latest \ --replicas=2 --port=8080 --dry-run=client -o yaml > ~/do108/day2/fids-web-deployment.yaml
i
Note

Templates are an OpenShift addition: a parameterised manifest describing several objects at once, stored in the cluster. oc process -f tmpl.yaml --parameters lists the parameters, oc process substitutes them, and oc new-app --template <name> deploys one directly. The openshift namespace ships several. You will not write one at this level, but you will meet them in the Developer Catalog.

!
Caution

DeploymentConfig, the older OpenShift-specific object, is deprecated from OpenShift 4.18. If you find one in an old manifest or a tutorial, treat it as legacy: write a standard Kubernetes Deployment instead.

Anatomy of a Deployment

~/do108/day2/fids-web-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: fids-web
  labels:
    app.kubernetes.io/name: fids-web
    app.kubernetes.io/part-of: fids
spec:
  replicas: 2
  selector:
    matchLabels:                     # which pods this Deployment owns
      app.kubernetes.io/name: fids-web
  template:                          # the pod that will be created, n times
    metadata:
      labels:
        app.kubernetes.io/name: fids-web    # MUST match the selector above
        app.kubernetes.io/part-of: fids
    spec:
      containers:
        - name: web
          image: registry.access.redhat.com/ubi9/httpd-24:latest
          ports:
            - containerPort: 8080
!
Caution

spec.selector.matchLabels and spec.template.metadata.labels must agree. If they do not, the API rejects the object — and the error message is not obvious the first time. When a Deployment refuses to be created, compare those two blocks before anything else.

9.2 Choosing a workload resource

ResourceKeeps running?Use it for
DeploymentYes, n identical interchangeable podsServers: web front ends, APIs, workers. Your default choice.
JobNo — runs to completion, retries on failureA one-off task: a database migration, an import, a backup.
CronJobCreates a Job on a scheduleRecurring tasks: the nightly reconciliation, a periodic export.
DaemonSetYes, one pod per nodeNode-level agents: log collectors, monitoring, storage daemons.
StatefulSetYes, with stable identity and per-pod storageDatabases and anything where replica 0 is not interchangeable with replica 1. Chapter 10.

Job and CronJob

~/do108/day2/bagtrack-cronjob.yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: bagtrack-nightly
spec:
  schedule: "*/2 * * * *"          # every two minutes, for the lab
  concurrencyPolicy: Forbid        # never two runs at once
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1
  jobTemplate:
    spec:
      backoffLimit: 3
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: reconcile
              image: registry.access.redhat.com/ubi9/ubi-minimal:latest
              command: ["/bin/sh", "-c", "echo Reconciled baggage; sleep 5; echo Done"]
FieldWhy it matters
scheduleStandard cron format. It is evaluated in the time zone of the control plane node running the controller — usually UTC. OpenShift 4.18 allows a time zone to be specified; without one, do not assume local time.
concurrencyPolicyAllow (default), Forbid, Replace. For anything that touches shared data, Forbid is what you want.
backoffLimitHow many failures before the Job gives up. Without it, a broken task retries for a very long time.
restartPolicyMust be OnFailure or Never in a Job — Always is rejected, because a task that always restarts never completes.
*JobsHistoryLimitHow many finished Jobs to keep. The defaults are generous enough to fill a project with completed pods over a weekend.

9.5 How pods reach each other

Every pod gets its own IP address, from a flat network that spans all nodes. Pods on different nodes, and in different namespaces, can reach each other directly, with no network address translation. On OpenShift that network is implemented by OVN-Kubernetes, the default network plug-in.

NetworkTypical rangeWho can reach it
Pod network10.128.0.0/14Pods, from anywhere in the cluster. Not your laptop.
Service network172.30.0.0/16Pods, from anywhere in the cluster. Not your laptop.

The problem a Service solves

Pod IP addresses are not stable. A pod that is rescheduled, updated or scaled gets a new address. Anything that wrote the old one down is now talking to nothing — or, worse, to somebody else's pod.

A Service is a stable IP address and a stable DNS name in front of a set of pods that is allowed to change. It finds its pods by label, keeps a list of endpoints, and balances requests across them, round robin by default.

~/do108/day2/fids-api-service.yaml
apiVersion: v1
kind: Service
metadata:
  name: fids-api
spec:
  selector:
    app: fids-api          # every pod carrying this label becomes an endpoint
  ports:
    - protocol: TCP
      port: 8080           # the port the Service listens on
      targetPort: 8080     # the port inside the pod

The two ports are different concepts and are often given the same value, which hides the distinction: port is what clients connect to; targetPort is where the traffic is delivered inside the container.

Names, not addresses

The cluster runs a DNS service (CoreDNS). Every Service gets a name:

Service DNS names
fids-api                                  # from a pod in the same project
fids-api.user1-platform                   # from a pod in another project
fids-api.user1-platform.svc.cluster.local # the fully qualified name

Inside a pod, /etc/resolv.conf is configured with the cluster DNS server and a search list, which is what makes the short form work:

[you@laptop ~]$ oc exec deployment/fids-web -- cat /etc/resolv.conf search user1-platform.svc.cluster.local svc.cluster.local cluster.local nameserver 172.30.0.10 options ndots:5
*
Tip

Configure your applications with the short service name — fids-api, or fids-api.user1-platform across projects. Never a pod IP, and never a service IP: the name survives everything, and the addresses do not.

Endpoints: the first thing to check when a service does not work

[you@laptop ~]$ oc get service fids-api -o wide NAME TYPE CLUSTER-IP PORT(S) AGE SELECTOR fids-api ClusterIP 172.30.118.42 8080/TCP 2m app=fids-api [you@laptop ~]$ oc get endpoints fids-api NAME ENDPOINTS AGE fids-api 10.128.2.44:8080,10.128.2.45:8080 2m
!
Caution

An empty ENDPOINTS column is the complete diagnosis: the Service's selector matches no pod. Either the labels differ, or no pod is ready. This produces a connection failure inside the cluster and an HTTP 503 through a Route, with nothing in any log — which is why it wastes so much time when you do not know to look here first.

9.7 Publishing to the outside world

A Service is reachable only from inside the cluster. Getting traffic in from outside is a separate decision, and there are four ways to make it.

TypeWhat it doesWhen
ClusterIPInternal only. The default.Almost always — for anything consumed by other pods.
NodePortOpens the same high port (30000–32767) on every node.Non-HTTP protocols, when there is no load balancer. Requires clients to reach the nodes directly, which is a security exposure.
LoadBalancerAsks the infrastructure for an external load balancer.Cloud environments. On bare metal it needs an implementation such as MetalLB, or it stays Pending for ever.
ExternalNameReturns a CNAME to an external DNS name.Giving an in-cluster name to something outside the cluster.
!
Caution

ExternalIP — assigning an arbitrary external address to a Service — is legacy from OpenShift 4.18, for security reasons. Prefer a Route, a LoadBalancer, or a NodePort with strict firewall rules.

The Route

For HTTP and HTTPS, none of the above is the normal answer. OpenShift ships an ingress controller — HAProxy — and a Route object that publishes a Service on a hostname:

[you@laptop ~]$ oc expose service fids-web [you@laptop ~]$ oc get route fids-web NAME HOST/PORT SERVICES PORT fids-web fids-web-user1-platform.apps.cluster-wnt8h... fids-web 8080

Without --hostname, the name is generated as <route>-<project>.<cluster route domain>. A wildcard DNS record sends every name under that domain to the ingress controller, which then dispatches on the HTTP Host header.

~/do108/day2/fids-web-route.yaml
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: fids-web
spec:
  to:
    kind: Service
    name: fids-web
  port:
    targetPort: 8080
!
Important

HTTP 503 from a route means the router found nothing to send the request to. Because the DNS wildcard resolves every name under the domain, a hostname with no matching Route — or a Route whose Service has no endpoints — still reaches the router, which answers 503. It is not a DNS problem and not an application problem. Check the Route, then the Service, then the endpoints, in that order.

i
Note

Ingress, the Kubernetes-standard object, also works: since OpenShift 4.18, creating an Ingress automatically creates a managed Route, which is removed with it. Use Ingress when a tool requires it; use Routes otherwise, because they support TLS re-encryption, passthrough and traffic splitting, which Ingress does not.

Scaling, and where the balancing happens

The Service balances traffic that arrives from inside the cluster. Traffic that arrives through a Route is balanced by the ingress controller itself, across the same endpoints. If a client must keep reaching the same pod, annotate the Route with a cookie name:

[you@laptop ~]$ oc scale deployment/fids-web --replicas=3 [you@laptop ~]$ oc annotate route fids-web router.openshift.io/cookie_name=fids

Summary

  • A Deployment owns a ReplicaSet, which owns pods; you write the Deployment and never touch the rest.
  • Deployment for servers, Job for a task that ends, CronJob for a schedule, DaemonSet for one pod per node, StatefulSet where identity and storage must persist.
  • DeploymentConfig is deprecated from OpenShift 4.18.
  • Pod IP addresses change; a Service gives a stable address and a DNS name, and finds its pods by label.
  • An empty endpoint list is the diagnosis for most “the service does not work” reports, and it is silent.
  • Services are internal; a Route publishes an HTTP service on a hostname, and 503 means the router had nowhere to send the request.
  • --dry-run=client -o yaml turns an imperative command into a manifest you can keep — which is how you get a reproducible application without typing YAML from memory.

Three questions to check yourself

Answer without looking back, then check

  1. A pod is in CrashLoopBackOff. oc logs prints nothing useful. What do you run, and why? oc logs <pod> --previous: the current container has only just started, and the reason is in the one that died. If that is also empty, the container never produced output — go back to oc describe and the events.
  2. A colleague says “the route gives me 503”. Give the three things you check, in order. The Route exists and points at the right Service; the Service exists and its selector is right; oc get endpoints is not empty. Nine times out of ten it is the third.
  3. Why does a Job refuse restartPolicy: Always? Because a task that is always restarted can never complete, and completion is the whole definition of a Job. Only OnFailure and Never are accepted.
