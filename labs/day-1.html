6.1 Containers, and what Kubernetes adds

A container is a process. Not a small virtual machine, not a lightweight operating system - a process, running on a normal Linux kernel, that has been given a restricted view of the system. Two kernel features do that work: namespaces isolate what the process can see (its processes, its network interfaces, its file system), and control groups (cgroups) limit what it can consume (CPU time, memory).

The process starts from a container image: a read-only bundle containing the application and every runtime dependency it needs. That is the whole point. The image carries its own libraries, so it runs identically on any host that has a container runtime, and two containers on the same host can use conflicting versions of the same library without either of them caring.

i
Note

The Open Container Initiative (OCI) standardises image format and runtime behaviour. Because the common implementations conform to it, an image built with one tool runs on any conforming platform - including OpenShift, whose runtime is CRI-O.

Where a single host stops being enough

You can run containers on one Linux host with podman and be perfectly happy. The trouble starts when you want the things that production actually requires:

What you wantWhat Kubernetes does about it
The application survives the loss of a machineWorkloads are described, not placed. If a node dies, the same description is satisfied on another node.
Components find each other without hard-coded addressesService discovery and an internal DNS: a component is reached by name, and the name resolves to whichever instances are healthy right now.
Capacity follows the loadHorizontal scaling: instances are added and removed, and traffic is spread across them.
A sick instance is replaced automaticallySelf-healing, driven by the health probes the application exposes.
A new version rolls out without an outageAutomated rollouts, with a rollback path if the new version misbehaves.
Settings and passwords live outside the imageConfig maps and secrets, injected at run time.

Everything in that right-hand column is a chapter of this book. Chapter 9 covers the first three, chapter 10 the last one, chapter 11 self-healing, chapter 12 rollouts.

The declarative model

This is the idea the whole platform is built on, and it is worth stating precisely, because everything else follows from it.

You do not tell Kubernetes what to do. You tell it what you want to be true, by writing a resource - a text document, in YAML or JSON - and submitting it to the API. Controllers inside the cluster then compare the current state with what you declared, and take whatever steps close the gap. They keep doing that, forever.

You writeThe cluster storesControllers do
“three replicas of this image”The object, in etcdStart three pods. One dies → start a fourth. A node dies → reschedule elsewhere.

Two consequences are worth internalising now:

  • Changes take time, and that is normal. Submitting an object returns immediately; the cluster converges afterwards. created in the output of a command means recorded, not running. Almost every confusion in your first week comes from that single distinction.
  • Undoing a manual change is not a fix. If you delete a pod that a controller is maintaining, the controller recreates it. To make something stop, you change what you declared - not what is running.

The pod

Kubernetes does not schedule containers. It schedules pods. A pod is one or more containers that are guaranteed to run on the same node, sharing a network namespace - the same IP address and port space - and able to share storage volumes.

Most pods contain exactly one container. Multi-container pods exist for a specific reason: when a helper process must live and die with the application and must reach it over localhost - a log shipper, a proxy, a component that prepares files before the main process starts.

6.2 What OpenShift adds

Kubernetes deliberately leaves gaps. It provides extension points and expects the administrator to fill them, because different organisations want different answers. OpenShift is Red Hat's set of answers, delivered as a supported, coherent product.

Developer workflowAn integrated container registry, source-to-image builds, and CI/CD pipelines, so that you do not have to assemble that chain yourself.
ObservabilityA monitoring stack (Prometheus, Alertmanager, Thanos) and a logging subsystem, deployed and configured for both the cluster and your applications.
Machine managementRed Hat Enterprise Linux CoreOS as the node operating system - immutable, managed by the cluster itself - plus installation and update procedures.
Authentication and authorisationIdentity providers, users, groups, and a role model that Kubernetes does not ship with out of the box.
IngressThe Route object and the router, which publish an application on a hostname without you writing an ingress controller.
Security defaultsSecurity Context Constraints, which decide what a pod is allowed to do - and which, by default, refuse to run your container as root. You will meet this in chapter 8.
A single consoleOne web interface for all of the above, in two perspectives.

6.3 Control plane, compute plane, and the trip your request takes

A cluster is a set of machines, called nodes. They come in two roles.

RoleWhat runs there
Control planeThe API server, the scheduler, the controllers, and etcd - the key-value store that holds every object in the cluster. This is the brain, and the single source of truth.
Compute plane
worker nodes		Your workloads. Each node runs a kubelet agent, which talks to the API server, and CRI-O, which actually starts and stops containers.

A machine can hold both roles - the training cluster may well be a single node doing everything - but in production they are separated for stability, security and manageability.

What happens when you create something

Follow one command all the way through. You type:

[you@laptop ~]$ oc create -f fids-web-pod.yaml pod/fids-web created
  1. The client sends an HTTPS request to the API server on port 6443, carrying your token and the object.
  2. The API server authenticates you - who are you? - then authorises the request - are you allowed to create a pod in this namespace? Then admission controllers inspect and possibly modify the object. This is where OpenShift's security constraints decide which user ID your container will run as.
  3. The object is written to etcd. At this exact moment your command returns created. Nothing is running yet.
  4. The scheduler notices a pod with no node assigned, picks a node that can satisfy its requirements, and writes that choice back through the API.
  5. The kubelet on that node notices that a pod is assigned to it, pulls the image if it is not already there, and asks CRI-O to start the containers.
  6. The kubelet reports status back through the API server, continuously. That is what you read in oc get pods.
*
Tip

Memorise the order of those six steps. It is a diagnostic map: a failure at step 2 gives you Forbidden, at step 4 a pod stuck in Pending, at step 5 an ImagePullBackOff, and at step 6 a CrashLoopBackOff. Knowing where the process stopped tells you where to look, before you know anything else.

Operators: the cluster administers itself

Almost every part of OpenShift is itself run by an operator - a controller that watches objects and keeps a piece of the platform in the state those objects describe. The DNS service, the ingress router, the monitoring stack, the authentication service: each has an operator, and each reports its own health as a ClusterOperator object.

That is why, in §6.6, checking whether a cluster is healthy will mostly mean reading a list of operators.

6.4 Projects and namespaces

A namespace is the Kubernetes unit of grouping: object names are unique within a namespace, and most objects live in one. A project is an OpenShift namespace with extra annotations - a display name, a description, a requester, and the ranges of user IDs that pods in it may use.

The relationship is one to one: every project is a namespace, and in OpenShift you generally create projects. In practice a project is your working boundary: what you can see by default, what your quotas apply to, and what gets deleted when you clean up.

[you@laptop ~]$ oc new-project ${U}-fids Now using project "user1-fids" on server "https://api.cluster-wnt8h...:6443". [you@laptop ~]$ oc project Using project "user1-fids" on server "https://api.cluster-wnt8h...:6443". [you@laptop ~]$ oc get projects NAME DISPLAY NAME STATUS user1-fids Active
!
Caution

oc delete project deletes everything inside it, including persistent volume claims and therefore, depending on the storage class, the data on them. It is also asynchronous: the project shows Terminating for a while, and you cannot create a project with the same name until it is gone.

6.5 The web console

The console is a client of the same API your CLI uses. It cannot do anything you could not do with oc, and it is subject to exactly the same permissions. What it is very good at is orientation: on a cluster you have never seen, it gives you the shape of things in two minutes.

Get its address from the CLI, so you never have to guess:

[you@laptop ~]$ oc whoami --show-console https://console-openshift-console.apps.cluster-wnt8h.dynamic.redhatworkshops.io

The perspective switcher is the first item in the sidebar. As a regular user you will find that several Administrator pages are empty or refused - Compute, Operators, cluster-wide Overview. That is not a bug; it is authorisation, and it is a useful thing to see once.

6.7 Reading the health of a cluster

“Is the cluster all right?” is a question you will be asked, often by someone standing behind you. There are five places to look, in this order.

Look atWhereWhat tells you something is wrong
Cluster operatorsAdministrator → Home → Overview → StatusAny operator not Available, or one that is Degraded or has been Progressing for a long time.
NodesCompute → NodesA node that is not Ready, or one under memory, disk or PID pressure.
AlertsObserve → AlertingAnything firing at Critical. Filter by severity; Info alerts are noise most of the time.
EventsHome → EventsRepeated Failed, BackOff or FailedScheduling reasons - usually the fastest route to the real problem.
UtilisationHome → Overview → Cluster utilisationCPU or memory close to capacity: the cluster is not broken, but it is about to refuse new pods.

Nodes, machines and machine configurations

Three words that are used almost interchangeably, and should not be:

  • a node is the Kubernetes object: a machine that can run pods;
  • a machine is the OpenShift object that describes that machine to the infrastructure, which is what makes it possible to create one on demand in a cloud;
  • a MachineConfig describes the files, services and versions that the node's operating system must have. The Machine Config Operator applies it and reboots nodes as needed.

You will not touch any of these at this level. You need to recognise them, because when a colleague says “the MCO is rolling”, it means nodes are rebooting one after another, and that is why your pods just moved.

Metrics and alerts

The cluster collects metrics from HTTP endpoints, using Prometheus. A ServiceMonitor object tells Prometheus where to scrape an application's /metrics endpoint; an alerting rule compares a metric against a condition and fires when it is no longer met. You will write both in the level 2 course; here you need to know that Observe → Metrics lets you run a query and see a graph, and Observe → Alerting lets you see what is currently wrong.

Events versus logs

*
Tip

Events are the cluster's account of what it did to your objects: scheduled, pulling, started, failed, backing off. Logs are your application's account of what it did. When something does not start, the answer is almost always in the events; when something starts and then behaves badly, the answer is in the logs. Looking in the wrong one is the most common waste of time in this job.

6.10 Watch out, and summary

The four mistakes everyone makes on day 1

MistakeWhat actually happens
Reading created as “it is running”The object is stored. Scheduling, pulling and starting come after, and any of them can fail. Always confirm with oc get pods.
Deleting a pod to “restart the application”If a Deployment owns it, a replacement appears within seconds - which is correct behaviour, and confusing the first time.
Working in the wrong projectCommands succeed and objects appear somewhere you are not looking. Put the namespace in your prompt (§3.3).
Reading logs when nothing has startedoc logs has nothing to show if the container never ran. Use oc describe and read the events.

Summary

  • A container is an isolated process created from an image that carries its own dependencies.
  • Kubernetes adds scheduling, service discovery, scaling, self-healing, rollouts and configuration management across a cluster of nodes.
  • The model is declarative: you record intent through the API, and controllers converge the cluster towards it, continuously.
  • OpenShift completes Kubernetes with a registry, builds, monitoring, logging, an immutable node operating system, authentication, routes, security defaults and a console - all built on Kubernetes extension points.
  • The control plane holds the API server, the scheduler, the controllers and etcd; the compute plane runs your pods through kubelet and CRI-O.
  • A project is a namespace with OpenShift annotations, and it is your working boundary.
  • Cluster health is read from cluster operators, node conditions, firing alerts, events and utilisation - in that order.

7.1 oc and kubectl: one tool, two names

Both commands are thin clients over the same HTTPS API. kubectl is the Kubernetes client; oc is a superset of it, shipped by Red Hat, which adds the commands that only make sense on OpenShift.

Only in ocWhat it does
oc login / oc logoutAuthenticate against the OpenShift OAuth server. kubectl has no login command at all - it expects a kubeconfig that someone else prepared.
oc new-project / oc project / oc projectsCreate and switch projects, which are an OpenShift concept.
oc new-appBuild an application from an image, a template or a source repository, in one command.
oc statusA summary of the current project and the relationships between its objects.
oc adm …Administrative subcommands: node logs, resource usage, diagnostics.
oc rsh, oc rsync, oc debugTroubleshooting conveniences you will use constantly in chapter 8.

Everything else - get, describe, create, apply, delete, explain, logs, exec, patch, edit - behaves identically in both. This book uses oc throughout, and points out the few places where the distinction matters.

!
Important

Client and server versions must stay close. A kubectl client is supported within one minor version of the cluster's Kubernetes version. Installing kubectl from your distribution's package manager and forgetting about it is the standard way of ending up four minor versions behind, with commands that silently drop fields. Take both binaries from the same OpenShift client archive, as you did in chapter 3, and check with oc version.

[you@laptop ~]$ oc version Client Version: 4.18.6 Kustomize Version: v5.4.2 Server Version: 4.18.6 Kubernetes Version: v1.31.6

7.2 Authenticating

Every request you make carries an identity. The API server first authenticates it - who are you? - and then authorises it - may you do this, here? A Forbidden error means authentication worked and authorisation did not, which is a much more useful message than it looks.

MethodCommandWhen
User and passwordoc login -u user1 <api-url>Interactive work. The password is prompted for and not echoed.
Tokenoc login --token=sha256~… --server=<api-url>Scripts, pipelines, automation. The recommended method outside a classroom: no password is stored anywhere, and the token expires.
Browseroc login --web <api-url>When the cluster uses corporate single sign-on and there is no password to type.
!
Caution

Passing a password on the command line - oc login -u user1 -p secret … - puts it in your shell history, in the process list, and often in a log. This book shows it once, here, so that you recognise it as something not to do. Use the interactive prompt during the course, and tokens at work.

Three commands tell you where you stand, and they are worth typing whenever anything surprises you:

[you@laptop ~]$ oc whoami user1 [you@laptop ~]$ oc whoami --show-server https://api.cluster-wnt8h.dynamic.redhatworkshops.io:6443 [you@laptop ~]$ oc project Using project "user1-fids" on server "https://api.cluster-wnt8h...:6443".

7.3 The essential command set

Nine commands cover almost everything you will do this week. They all follow the same grammar:

The shape of every command
oc <verb> <resource-type> [<name>] [-n <namespace>] [options]
CommandWhat it is for, and the option that matters
oc getList, briefly. -o wide adds columns the default view hides - the node, the pod IP, the image. -w watches for changes.
oc describeOne object, in detail, in human-readable form - including its events, at the bottom. This is where you look when something does not start.
oc create -fCreate objects from a file. Fails if the object already exists.
oc apply -fCreate or update from a file. Safe to run repeatedly - the verb to prefer for anything you keep in a file.
oc deleteRemove an object. Remember that a controller may recreate it.
oc explainThe documentation of a resource, from your own cluster, at your cluster's version.
oc logsThe output of a container. -c selects one container in a multi-container pod; --previous reads the container that died.
oc execRun a command inside a running container.
oc get eventsWhat the cluster did, and why it stopped doing it. Always add --sort-by .metadata.creationTimestamp.

Namespaces, and the three ways to get them wrong

Every namespaced command applies to the current project unless told otherwise:

# the current project [you@laptop ~]$ oc get pods # a named project, for this command only [you@laptop ~]$ oc get pods -n openshift-ingress # every project you are allowed to read [you@laptop ~]$ oc get pods -A # change the current project for good [you@laptop ~]$ oc project ${U}-fids

Two shortcuts worth knowing on the first day

# Short names save typing; oc api-resources lists them all [you@laptop ~]$ oc get po,svc,deploy # A summary of the whole project in one command [you@laptop ~]$ oc get all [you@laptop ~]$ oc status
i
Note

oc get all is a convenience, not a promise: it iterates over a fixed list of common types. It does not show config maps, secrets or persistent volume claims. Do not use it to check that a project is empty before deleting things.

    i
    Note

    This is the timeline of Lab 6.1, and it is the single most useful command in this chapter.

7.5 The shape of an object

Every object in the API - pod, service, node, route, anything - has the same four top-level fields, plus one the cluster writes for you.

The universal structure
apiVersion: v1          # which schema, and which version of it
kind: Pod               # which kind of object
metadata:               # identity: name, namespace, labels, annotations
  name: fids-web
  namespace: user1-fids
  labels:
    app.kubernetes.io/name: fids-web
spec:                   # WHAT YOU WANT - you write this
  containers:
    - name: web
      image: registry.access.redhat.com/ubi9/httpd-24:latest
status:                 # WHAT IS - the cluster writes this, never you
  phase: Running
  podIP: 10.128.2.41
  conditions:
    - type: Ready
      status: "True"
      lastTransitionTime: "2026-09-08T09:14:02Z"
FieldWho writes itWhat it is
apiVersionYouAPI group and version, as group/version. Core objects have no group and are simply v1; a Deployment is apps/v1.
kindYouThe schema. Capitalised, singular: Pod, Service, Deployment.
metadataYou, mostlyName, namespace, labels, annotations. The cluster adds uid, creationTimestamp and resourceVersion.
specYouThe desired state. This is the whole of your job.
statusThe clusterThe observed state. Read it; never write it.

Conditions

status usually carries a list of conditions, and reading them is a skill worth acquiring today. Each condition has five fields:

FieldExampleMeaning
typeContainersReadyWhat is being asserted.
status"False"Whether it currently holds. A string, not a boolean.
reasonContainersNotReadyA machine-readable cause.
messagecontainers with unready status: [web]The human-readable version. Read it fully.
lastTransitionTime2026-09-08T09:14:02ZWhen it last changed - which tells you whether the problem is new or old.
*
Tip

A condition whose status is "False" is not always bad news. For a node, MemoryPressure: "False" is exactly what you want. Read the type before you read the status.

Labels and selectors

Labels are key–value pairs in metadata.labels. They look decorative and they are structural: Services find their pods by label, Deployments own their pods by label, and every -l filter you type uses them.

[you@laptop ~]$ oc get pods -l app.kubernetes.io/part-of=fids [you@laptop ~]$ oc label pod fids-web-6b9c7d5f4c-2xk9p tier=frontend [you@laptop ~]$ oc get pods -l 'tier in (frontend,backend)'
!
Caution

A selector that matches nothing does not produce an error. It produces a Service with no endpoints, which answers every request with a connection failure or an HTTP 503, and gives you nothing to search for. When a service does not work, check the labels before anything else. Chapter 9 has a lab built entirely around this.

7.6 Discovering the API from the cluster

You will regularly need a field name you do not remember, on a resource type you have never used, on a cluster with no internet access. The cluster knows its own API, and will tell you.

oc api-resources - what types exist here

[you@laptop ~]$ oc api-resources NAME SHORTNAMES APIVERSION NAMESPACED KIND configmaps cm v1 true ConfigMap persistentvolumeclaims pvc v1 true PersistentVolumeClaim pods po v1 true Pod services svc v1 true Service deployments deploy apps/v1 true Deployment ... # Only what lives inside a namespace - and how many types that is [you@laptop ~]$ oc api-resources --namespaced=true -o name | wc -l # Only the core group (no group name at all) [you@laptop ~]$ oc api-resources --api-group '' # Only one group [you@laptop ~]$ oc api-resources --api-group apps --sort-by name

Four columns, four pieces of information:

  • SHORTNAMES - what you can type instead. oc get cm, oc get pvc.
  • APIVERSION - the group and version, which is what you put in apiVersion.
  • NAMESPACED - whether the object lives in a namespace. Nodes and persistent volumes do not; pods and services do. This decides whether -n means anything.
  • KIND - what you put in kind.

oc explain - what fields a type has

[you@laptop ~]$ oc explain pod KIND: Pod VERSION: v1 DESCRIPTION: Pod is a collection of containers that can run on a host... FIELDS: apiVersion <string> kind <string> metadata <ObjectMeta> spec <PodSpec> status <PodStatus> # Walk down into the structure, one dot at a time [you@laptop ~]$ oc explain pod.spec [you@laptop ~]$ oc explain pod.spec.containers [you@laptop ~]$ oc explain pod.spec.containers.resources # Everything at once, names only, no prose [you@laptop ~]$ oc explain pod --recursive | head -40
*
Tip

This is the answer to “what is the exact spelling of that field?” - and it answers for your cluster's version, which the internet does not. Get into the habit now: oc explain before searching, always.

7.8 Getting exactly the value you need

oc get prints a table designed for humans. As soon as you want one value - for a script, for a check, for a colleague - you need a different output format. There are five, and you should know three of them well.

FormatNeedsBest for
-o wideNothingThe same table with the columns that were hidden. Free, always try it first.
-o yaml / -o jsonNothingThe whole object, exactly as the API holds it. For reading, and for saving.
-o jsonpath=…NothingOne value, in a script. Built into the client, so it works everywhere.
-o custom-columns=…NothingYour own table, with the columns you actually care about.
| jq / | yqAn extra tool installedComplex filtering and reshaping. Powerful, but not present on every machine.
!
Important

jq and yq are excellent and are used throughout the official course material. They are also extra installations, and this course assumes only the oc client. Everything in the labs below is done with JSONPath and custom columns, which are built in. If you have jq, use it - the equivalents are given. If you do not, you lose nothing.

JSONPath

# One field of one object [you@laptop ~]$ oc get pod fids-web-6b9c7d5f4c-2xk9p -o jsonpath='{.status.podIP}{"\n"}' 10.128.2.41 # One field of every object in a list [you@laptop ~]$ oc get pods -o jsonpath='{.items[*].metadata.name}{"\n"}' # A loop, with your own formatting [you@laptop ~]$ oc get pods -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.podIP}{"\n"}{end}' fids-web-6b9c7d5f4c-2xk9p 10.128.2.41 # The route hostname - you will use this one every day [you@laptop ~]$ oc get route fids-web -o jsonpath='{.spec.host}{"\n"}'
*
Tip

Always finish a JSONPath expression with {"\n"}. Without it the value and your next shell prompt end up on the same line, and you will eventually copy the prompt into a script.

Custom columns

[you@laptop ~]$ oc get pods -o custom-columns=\ NAME:.metadata.name,\ NODE:.spec.nodeName,\ IP:.status.podIP,\ IMAGE:.spec.containers[0].image NAME NODE IP IMAGE fids-web-6b9c7d5f4c-2xk9p worker-1 10.128.2.41 registry.access.redhat.com/ubi9/httpd-24:latest

Go templates, and the tools

# Go template - same idea, different syntax [you@laptop ~]$ oc get pods -o go-template='{{range .items}}{{.metadata.name}}{{"\n"}}{{end}}' # With jq, if it happens to be installed [you@laptop ~]$ oc get pods -o json | jq -r '.items[].status.podIP' # With yq [you@laptop ~]$ oc get pods -o yaml | yq '.items[0].status.podIP'
i
Note

Two unrelated programs are called yq, and their syntaxes are incompatible. If a yq command from the internet fails on your machine, you probably have the other one.

What not to parse

!
Caution

Never build a script on the output of oc describe. It is designed for humans and its layout changes between versions - your script will break on an upgrade, silently, at the worst moment. Anything a machine reads should come from -o json, -o yaml, -o jsonpath or -o custom-columns.

7.10 Cluster health from the command line

Everything you read from the console in chapter 6 has a command-line equivalent. These need cluster-wide rights, so your trainer demonstrates them; write them down, because they are what you will run on your own cluster.

# The version, and whether the last update completed [admin@laptop ~]$ oc get clusterversion # The platform's own operators - the fastest global health check there is [admin@laptop ~]$ oc get clusteroperators [admin@laptop ~]$ oc get co | grep -v 'True *False *False' # only what is not fine # Add-on operators installed on top [admin@laptop ~]$ oc get operators # Nodes, and their conditions [admin@laptop ~]$ oc get nodes [admin@laptop ~]$ oc get node <name> -o jsonpath=\ '{range .status.conditions[*]}{.type}{"\t"}{.status}{"\t"}{.message}{"\n"}{end}' # Consumption [admin@laptop ~]$ oc adm top nodes [admin@laptop ~]$ oc adm top pods -A --sum # A node's own service logs [admin@laptop ~]$ oc adm node-logs <name> -u kubelet --tail 20 # A shell on a node, for reading only [admin@laptop ~]$ oc debug node/<name> sh-5.1# chroot /host sh-5.1# for s in kubelet crio; do echo -n "$s: "; systemctl is-active $s; done # Everything Red Hat Support will ask for, in one command [admin@laptop ~]$ oc adm must-gather --dest-dir ~/must-gather [admin@laptop ~]$ tar caf must-gather.tar.gz must-gather/ # The same, narrowed to one component [admin@laptop ~]$ oc adm inspect clusteroperator/authentication --since 10m --dest-dir ~/inspect
!
Important

oc adm must-gather creates pods on the cluster and can produce hundreds of megabytes. Run it when you are opening a support case, not out of curiosity - and never in a loop. Attach the archive and the cluster ID that the command prints; without the ID, Support cannot correlate anything.

7.12 Watch out, and summary

Watch out

TrapWhat to do instead
A kubectl several minor versions from the clusterUse the kubectl from the OpenShift client archive. Check with oc version.
Parsing oc describe in a scriptUse -o jsonpath or -o custom-columns. The layout of describe is not an interface.
Passwords on the command lineThe interactive prompt, or a token.
Forgetting -n and working in the wrong projectPut the namespace in your prompt; run oc project when in doubt.
Applying a file exported with -o yamlStrip status, uid, resourceVersion and creationTimestamp first - chapter 9.
oc get all used as “show me everything”It is a fixed shortlist. Config maps, secrets and PVCs are not in it.

Summary

  • oc is kubectl plus the OpenShift-specific commands; keep client and server within one minor version.
  • Authenticate interactively during the course and with tokens everywhere else; never put a password on a command line.
  • Every object has apiVersion, kind, metadata, spec - which you write - and status, which the cluster writes.
  • Conditions carry type, status, reason, message and lastTransitionTime: read all five before concluding anything.
  • The cluster documents its own API: oc api-resources for the types, oc explain for the fields.
  • For one exact value use JSONPath or custom columns - never text-processing on describe.
  • Cluster health from the CLI: clusterversion, clusteroperators, nodes, adm top, events; and must-gather when you open a case.
