Day 4 openingChanging it without breaking it

Three days of building. Today is about the thing that happens to every application that survives long enough to matter: it changes.

Where we start

Your platform is in good shape. The configuration is external, the data persists, the probes work, the resources are declared. And one thing is still quietly wrong with every deployment you have made this week: they all reference :latest.

That means nobody can say which version is running, a node drain can change it, a scale-up can produce two versions behind one Service, and a rollback restores a name rather than an image. This morning fixes that, and then teaches you to change a running application deliberately - gradually, measurably, and reversibly.

Chapter 12Managing application updates

By the end of this chapter you will be able to

  • say exactly which image a running pod uses, and prove it;
  • explain why a floating tag is a promise nobody made, and pin an image by digest;
  • choose between a rolling update and a recreate, and set the surge and unavailability yourself;
  • watch a rollout, recognise a failed one, and roll it back in one command;
  • use an image stream to give a moving target a stable, reversible name;
  • attach an image change trigger so that a tag change deploys itself.

12.1 Which image is actually running

Chapter 8 introduced the four parts of an image reference. This chapter is about the consequence of getting them wrong.

The same image, two ways to name it
registry.access.redhat.com/ubi9/httpd-24:latest          # a tag: can be moved
registry.access.redhat.com/ubi9/httpd-24@sha256:9f2a...  # a digest: cannot

A floating tag - latest, 1, 9.6 - is reassigned by the publisher whenever they choose, without notice. The distinction between a floating tag and a fixed one is convention, not a technical control: nothing in the registry stops any tag from moving.

The failure that follows

Two scenarios, both of which happen in real clusters, and neither of which involves anybody deploying anything:

  • A pod is rescheduled. The node it lands on has no copy of the image, so it pulls one - and gets whatever the tag points to today. Your application changed version because a node was drained.
  • An application is scaled up. The new replicas pull a newer image than the originals. You now run two versions behind one Service, and requests behave differently depending on which pod answers.
!
Important

Three ways to make a deployment reproducible: a tag that you know never moves, an image stream (§12.6), or the digest. Only the digest is a guarantee - it is the hash of the image content, so it cannot refer to anything else.

# Find the digest of the tag you are using today [you@laptop ~]$ oc image info registry.access.redhat.com/ubi9/httpd-24:latest \ --filter-by-os linux/amd64 | grep -E '^(Name|Digest):' Name: registry.access.redhat.com/ubi9/httpd-24:latest Digest: sha256:9f2a1c...c41b # What a running pod really uses - the imageID, not the image field [you@laptop ~]$ oc get pod <pod> -o jsonpath=\ '{.status.containerStatuses[0].image}{"\n"}{.status.containerStatuses[0].imageID}{"\n"}'
*
Tip

spec.containers[].image is what you asked for; status.containerStatuses[].imageID is what the node actually resolved. When two pods of the same deployment behave differently, compare their imageID values - if they differ, you have found your answer in ten seconds.

12.2 How images reach a node

imagePullPolicy decides whether a node reuses the copy it already has:

PolicyBehaviourDefault when
IfNotPresentUse the local copy if there is one. A moved tag is not noticed.The image reference has a tag other than latest, or a digest.
AlwaysAsk the registry for the current digest every time; pull only if it differs from the local copy.The reference uses latest, or has no tag at all.
NeverNever pull. The image must already be on the node, or the pod fails.Never a default - you choose it deliberately.
i
Note

Deleting a pod does not delete its image. The kubelet's garbage collector runs about every five minutes and removes the oldest unused images once the image file system passes roughly 85 % usage, stopping at about 80 %. Those thresholds are cluster settings. In practice: do not expect an image to disappear because you stopped using it, and do not be surprised when a node suddenly frees several gigabytes.

12.3 Lab 12.1 - Pin the flight board

Guided lab Lab 12.1 - From a tag to a digest
Goal. Establish exactly which image is running, and make it stop being able to change. Time. 20 minutes.

  1. Ask what you deployed, and what is running:

    [you@laptop ~]$ oc project ${U}-platform [you@laptop ~]$ oc get deployment fids-web -o jsonpath=\ '{.spec.template.spec.containers[0].image}{"\n"}' registry.access.redhat.com/ubi9/httpd-24:latest [you@laptop ~]$ oc get pods -l app=fids-web -o jsonpath=\ '{range .items[*]}{.metadata.name}{"\t"}{.status.containerStatuses[0].imageID}{"\n"}{end}'

    Every pod resolved the tag to the same digest - today. Nothing keeps it that way.

  2. Capture the digest that the tag currently points to:

    [you@laptop ~]$ DIGEST=$(oc image info registry.access.redhat.com/ubi9/httpd-24:latest \ --filter-by-os linux/amd64 | awk '/^Digest:/{print $2}') [you@laptop ~]$ echo $DIGEST sha256:9f2a1c...c41b

  3. Pin the deployment to it:

    [you@laptop ~]$ oc set image deployment/fids-web \ httpd-24=registry.access.redhat.com/ubi9/httpd-24@$DIGEST [you@laptop ~]$ oc rollout status deployment/fids-web [you@laptop ~]$ oc get deployment fids-web -o jsonpath=\ '{.spec.template.spec.containers[0].image}{"\n"}'
    i
    Note

    oc set image takes <container-name>=<image>. Find the container name with oc get deployment fids-web -o wide - the CONTAINERS column. It is not always the deployment name.

  4. Prove that scaling is now safe:

    [you@laptop ~]$ oc scale deployment/fids-web --replicas=4 [you@laptop ~]$ oc get pods -l app=fids-web -o jsonpath=\ '{range .items[*]}{.status.containerStatuses[0].imageID}{"\n"}{end}' | sort -u | wc -l 1

    One distinct image across every replica, and it will still be one next month. With a floating tag that count is a matter of luck.

  5. See the pull policy change with the reference:

    [you@laptop ~]$ oc get deployment fids-web -o jsonpath=\ '{.spec.template.spec.containers[0].imagePullPolicy}{"\n"}' IfNotPresent

    With :latest it was Always; with a digest, IfNotPresent - and that is correct, because a digest cannot point at anything new.

  6. Record why you did it. Future you will want to know:

    [you@laptop ~]$ oc annotate deployment/fids-web \ kubernetes.io/change-cause="Pinned httpd-24 to digest for reproducibility" --overwrite [you@laptop ~]$ oc rollout history deployment/fids-web [you@laptop ~]$ oc scale deployment/fids-web --replicas=2
?
Check

The deployment references a digest; every replica reports the same imageID; and you can explain, in one sentence, what would have happened on a node drain if you had left the tag in place.

12.4 Rollout strategies

Changing anything in a Deployment's pod template starts a rollout. The deployment creates a new ReplicaSet for the new template and moves replicas from the old one to the new one. How it moves them is the strategy.

StrategyHowChoose it when
RollingUpdate
the default		New pods start, become ready, and only then are old ones removed. Both versions run at once.Almost always. Requires that the two versions can coexist - same database schema, compatible APIs.
RecreateEvery old pod is stopped, then the new ones start. Guaranteed downtime.The versions cannot coexist: an incompatible schema change, or a migration that must run between them.
Controlling a rolling update
apiVersion: apps/v1
kind: Deployment
metadata:
  name: fids-web
spec:
  replicas: 4
  revisionHistoryLimit: 10       # how many old ReplicaSets to keep for rollback
  progressDeadlineSeconds: 600   # after this, the rollout is declared failed
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1                # at most 5 pods during the update
      maxUnavailable: 0          # never fewer than 4 serving
  selector:
    matchLabels:
      app: fids-web
  template:
    metadata:
      labels:
        app: fids-web
    spec:
      containers:
        - name: httpd-24
          image: registry.access.redhat.com/ubi9/httpd-24:latest
SettingWhat it buys you
maxSurgeHow many pods may exist above the desired count. Higher means faster, and needs spare capacity.
maxUnavailableHow many may be missing below it. 0 means no reduction in capacity at any moment - the safe choice for a front end.
progressDeadlineSecondsHow long a stalled rollout is tolerated before the deployment reports ProgressDeadlineExceeded. Nothing is undone; you are simply told.
!
Caution

A rolling update without a readiness probe is a rolling outage. With no probe, a pod counts as available the moment its process starts - so the old pod is removed while the new one is still loading, and every request in between fails. Chapter 11 was the prerequisite for this chapter.

Watching, and grouping changes

# Follow a rollout to its conclusion; exits non-zero if it fails [you@laptop ~]$ oc rollout status deployment/fids-web # Group several changes into ONE rollout instead of three [you@laptop ~]$ oc rollout pause deployment/fids-web [you@laptop ~]$ oc set image deployment/fids-web httpd-24=<new-image> [you@laptop ~]$ oc set env deployment/fids-web TERMINAL=T2 [you@laptop ~]$ oc set resources deployment/fids-web --limits memory=512Mi [you@laptop ~]$ oc rollout resume deployment/fids-web

12.5 Rolling back

Each pod template revision keeps its own ReplicaSet, scaled to zero. That is what makes a rollback fast: the old definition still exists, and returning to it is a scale operation, not a redeployment.

[you@laptop ~]$ oc rollout history deployment/fids-web REVISION CHANGE-CAUSE 1 <none> 3 Pinned httpd-24 to digest for reproducibility 4 Upgrade to httpd on UBI 8 [you@laptop ~]$ oc rollout history deployment/fids-web --revision 3 [you@laptop ~]$ oc rollout undo deployment/fids-web # previous revision [you@laptop ~]$ oc rollout undo deployment/fids-web --to-revision 3 # a specific one
!
Important

OpenShift does not roll back a failed rollout for you. A bad image name or a readiness probe that never passes leaves the deployment stuck, with the old pods still serving and the new ones failing. That is deliberate - it protects the running version - but it means oc rollout undo is a decision a human has to take. Watch your rollouts.

!
Caution

Rolling back a deployment that references a floating tag may not restore the image you had. The rollback restores the pod template, which says :latest - and :latest may now be the version you are trying to escape. Digests and image streams both solve this; nothing else does.

*
Tip

The CHANGE-CAUSE column comes from the kubernetes.io/change-cause annotation, and it is empty unless you set it. Annotate after every deliberate change; at three in the morning, a history of <none> tells you nothing at all.

12.6 Lab 12.2 - Roll out, fail, roll back

Guided lab Lab 12.2 - A rollout, watched from both sides
Goal. Perform a clean rolling update with no lost requests, then a failed one, and recover. Time. 30 minutes.

  1. Set the strategy explicitly and make sure a readiness probe exists:

    [you@laptop ~]$ oc scale deployment/fids-web --replicas=4 [you@laptop ~]$ oc set probe deployment/fids-web --readiness --get-url http://:8080/ \ --period-seconds 2 --failure-threshold 2 [you@laptop ~]$ oc patch deployment fids-web -p \ '{"spec":{"strategy":{"rollingUpdate":{"maxSurge":1,"maxUnavailable":0}}}}' [you@laptop ~]$ oc rollout status deployment/fids-web

  2. Start a request loop in a second terminal and leave it running. This is the whole point of the lab - you are measuring the update, not just performing it:

    [you@laptop ~]$ FIDS=$(oc get route fids-web -o jsonpath='{.spec.host}') [you@laptop ~]$ while true; do curl -s -o /dev/null -w '%{http_code} ' http://$FIDS/; sleep 0.3; done

  3. Roll out a new version in the first terminal:

    [you@laptop ~]$ oc set image deployment/fids-web \ httpd-24=registry.access.redhat.com/ubi8/httpd-24:latest [you@laptop ~]$ oc annotate deployment/fids-web \ kubernetes.io/change-cause="Upgrade to httpd on UBI 8" --overwrite [you@laptop ~]$ oc rollout status deployment/fids-web [you@laptop ~]$ oc get replicaset

    Two ReplicaSets: the old one scaling to zero, the new one scaling up. In the second terminal, every response should still be 200.

    *
    Tip

    Repeat this step with maxUnavailable: 1 and no readiness probe. The loop will show a handful of 503s. That single comparison is the most persuasive argument for probes you will ever make to a colleague.

  4. Confirm the new version really is new:

    [you@laptop ~]$ oc exec deployment/fids-web -- cat /etc/redhat-release

  5. Now break a rollout on purpose:

    [you@laptop ~]$ oc set image deployment/fids-web \ httpd-24=registry.access.redhat.com/ubi9/httpd-24:does-not-exist [you@laptop ~]$ oc rollout status deployment/fids-web --timeout=60s Waiting for deployment "fids-web" rollout to finish: 1 out of 4 new replicas have been updated... error: timed out waiting for the condition [you@laptop ~]$ oc get pods -l app=fids-web

    One new pod in ImagePullBackOff, four old pods still Running. Your request loop never faltered: the deployment refused to remove healthy pods for broken ones. This is the platform protecting you.

    [you@laptop ~]$ oc describe deployment fids-web | grep -A3 Conditions

  6. Recover:

    [you@laptop ~]$ oc rollout history deployment/fids-web [you@laptop ~]$ oc rollout undo deployment/fids-web [you@laptop ~]$ oc rollout status deployment/fids-web [you@laptop ~]$ oc get pods -l app=fids-web

    One command, a few seconds, no redeployment: the previous ReplicaSet was still there, scaled to zero.

  7. Try the other strategy, and watch what it costs:

    [you@laptop ~]$ oc patch deployment fids-web --type=json \ -p='[{"op":"replace","path":"/spec/strategy","value":{"type":"Recreate"}}]' [you@laptop ~]$ oc set env deployment/fids-web ROLLOUT_TEST=1 [you@laptop ~]$ oc rollout status deployment/fids-web

    Watch the second terminal: a burst of 503s while every pod is down at once. That is the price of Recreate, and it is why you only choose it when the two versions genuinely cannot coexist. Put it back:

    [you@laptop ~]$ oc patch deployment fids-web --type=json \ -p='[{"op":"replace","path":"/spec/strategy","value":{"type":"RollingUpdate","rollingUpdate":{"maxSurge":1,"maxUnavailable":0}}}]' [you@laptop ~]$ oc set env deployment/fids-web ROLLOUT_TEST- [you@laptop ~]$ oc rollout status deployment/fids-web

    Stop the request loop with Ctrl-C.

?
Check

You performed an update with zero non-200 responses, produced a failed rollout that harmed nothing, recovered with one command, and measured the cost of Recreate. You can state why the failed rollout did not roll itself back.

12.7 Image streams

An image stream is an OpenShift object that sits between your workloads and a registry. It holds one or more image stream tags, and each tag records the digest of the image it currently points to - plus the history of the digests it pointed to before.

PropertyWhy it matters
A tag resolves to a digestEvery pod created from it gets the same bytes, even months apart and on a new node.
It does not follow the registrySomeone moving :latest upstream changes nothing for you until you decide. That isolation is the feature.
It keeps a historyReverting a tag genuinely restores the previous image - which a plain rollback of a floating tag cannot do.
Tags can come from anywhereOne stream can hold tags from different registries and repositories, behind one internal name.
Optional pull-through cache--reference-policy local caches the image in the cluster's own registry, which helps when the public registry is slow, throttled or unreachable.
# Create a stream and point a tag at a real image [you@laptop ~]$ oc create is fids-web [you@laptop ~]$ oc tag registry.access.redhat.com/ubi9/httpd-24:latest fids-web:v1 # Or in one command, importing immediately [you@laptop ~]$ oc import-image fids-web:v1 \ --from=registry.access.redhat.com/ubi9/httpd-24:latest --confirm # Re-import every 15 minutes, and cache locally [you@laptop ~]$ oc tag registry.access.redhat.com/ubi9/httpd-24:latest fids-web:v1 \ --scheduled --reference-policy local [you@laptop ~]$ oc describe is fids-web [you@laptop ~]$ oc get istag

Using a short name

Three conditions must all hold before a Deployment may write fids-web:v1 instead of a full registry reference:

  1. the image stream is in the same project as the Deployment;
  2. local lookup is enabled on the stream;
  3. the Deployment uses the short name, not the registry path.
[you@laptop ~]$ oc set image-lookup fids-web [you@laptop ~]$ oc set image-lookup NAME LOCAL fids-web true [you@laptop ~]$ oc create deployment fids-web-is --image fids-web:v1
i
Note

oc create istag can only create a tag, never update one. oc tag and oc import-image can do both, so prefer them - a script built on oc create istag fails the second time it runs.

Alias tags: a floating tag you control

# v1 and v2 are fixed; "stable" is an alias you move deliberately [you@laptop ~]$ oc tag registry.access.redhat.com/ubi9/httpd-24:latest fids-web:v1 [you@laptop ~]$ oc tag registry.access.redhat.com/ubi8/httpd-24:latest fids-web:v2 [you@laptop ~]$ oc tag --alias fids-web:v1 fids-web:stable # … test v2 … [you@laptop ~]$ oc tag --alias fids-web:v2 fids-web:stable # promote [you@laptop ~]$ oc tag --alias fids-web:v1 fids-web:stable # roll back

12.8 Image change triggers

An image stream tag that changes does not, by itself, redeploy anything. An image change trigger connects the two: when the tag resolves to a new digest, the Deployment's image field is rewritten and a normal rollout starts.

[you@laptop ~]$ oc set triggers deployment/fids-web-is \ --from-image fids-web:stable --containers fids-web [you@laptop ~]$ oc set triggers deployment/fids-web-is NAME TYPE VALUE AUTO deployments/fids-web-is config true deployments/fids-web-is image fids-web:stable true
TriggerFires onTurned off by
configAny change to the pod template - environment, probes, resources.oc rollout pause, restored by oc rollout resume.
imageThe image stream tag resolving to a new digest.oc set triggers … --manual, restored with --auto.
!
Important

Triggers are per container: --containers takes the container's name, which you find in the CONTAINERS column of oc get deployment -o wide. And think about blast radius before you combine --scheduled with triggers: one upstream image change will then redeploy every workload watching that tag, at once, unattended.

12.9 Lab 12.3 - A stream, a trigger, and a one-word rollback

Guided lab Lab 12.3 - Deploying by moving a tag
Goal. Build an image stream with two versions and an alias, deploy through it, and promote and roll back by moving one tag. Time. 30 minutes.

  1. Create the stream with two real versions:

    [you@laptop ~]$ oc project ${U}-platform [you@laptop ~]$ oc tag registry.access.redhat.com/ubi9/httpd-24:latest fids-web:v1 [you@laptop ~]$ oc tag registry.access.redhat.com/ubi8/httpd-24:latest fids-web:v2 [you@laptop ~]$ oc get istag [you@laptop ~]$ oc describe is fids-web

    Each tag has resolved to a digest. Note the asterisk in the description output: it marks the current image for each tag.

  2. Create the alias that your workload will actually follow:

    [you@laptop ~]$ oc tag --alias fids-web:v1 fids-web:stable [you@laptop ~]$ oc get istag

  3. Enable local lookup and deploy by short name:

    [you@laptop ~]$ oc set image-lookup fids-web [you@laptop ~]$ oc create deployment board --image fids-web:stable --replicas=2 --port=8080 [you@laptop ~]$ oc set probe deployment/board --readiness --get-url http://:8080/ \ --period-seconds 2 --failure-threshold 2 [you@laptop ~]$ oc set resources deployment/board --requests cpu=50m,memory=64Mi --limits memory=256Mi [you@laptop ~]$ oc rollout status deployment/board

    Look at what was actually recorded in the deployment:

    [you@laptop ~]$ oc get deployment board -o jsonpath=\ '{.spec.template.spec.containers[0].image}{"\n"}'

    Not fids-web:stable - a full internal registry reference ending in a digest. The short name was resolved once, to something immutable.

  4. Attach the trigger:

    [you@laptop ~]$ oc get deployment board -o wide # read the CONTAINERS column [you@laptop ~]$ oc set triggers deployment/board --from-image fids-web:stable --containers fids-web [you@laptop ~]$ oc set triggers deployment/board

  5. Promote v2 by moving one tag, and deploy nothing:

    [you@laptop ~]$ oc exec deployment/board -- cat /etc/redhat-release [you@laptop ~]$ oc tag --alias fids-web:v2 fids-web:stable [you@laptop ~]$ oc rollout status deployment/board [you@laptop ~]$ oc exec deployment/board -- cat /etc/redhat-release

    The release string changed. You did not touch the Deployment: the trigger rewrote its image field and a normal rolling update followed.

  6. Roll back the same way:

    [you@laptop ~]$ oc tag --alias fids-web:v1 fids-web:stable [you@laptop ~]$ oc rollout status deployment/board [you@laptop ~]$ oc exec deployment/board -- cat /etc/redhat-release [you@laptop ~]$ oc rollout history deployment/board

    This is the difference §12.5 warned about: with a floating registry tag, a rollback restores a name. With an image stream, it restores a digest.

  7. Take manual control, which is what you do during a freeze:

    [you@laptop ~]$ oc set triggers deployment/board --from-image fids-web:stable \ --containers fids-web --manual [you@laptop ~]$ oc tag --alias fids-web:v2 fids-web:stable [you@laptop ~]$ oc exec deployment/board -- cat /etc/redhat-release

    The tag moved and nothing was deployed. Re-enable it when the freeze ends:

    [you@laptop ~]$ oc set triggers deployment/board --from-image fids-web:stable \ --containers fids-web --auto [you@laptop ~]$ oc rollout status deployment/board

  8. Clean up the extra deployment, keeping the stream:

    [you@laptop ~]$ oc delete deployment board
?
Check

Moving the alias deployed a new version with no oc set image; moving it back restored the old one; and with --manual the tag moved while the workload stayed put. You can explain what a Deployment stores when you give it a short image-stream name.

12.10 Workshop 12.4 - Update the gate planner

Workshop Workshop 12.4 - Someone else's application
Goal. Update an application you did not write, safely, with a measured result. Time. 25 minutes.

The situation. The gate planning team has asked you to move gateplan-web from its current image to a new one. They will not accept a maintenance window, and they want to be able to go back within a minute if anything is wrong.

Setup:

[you@laptop ~]$ oc new-project ${U}-gateplan2 [you@laptop ~]$ oc create deployment gateplan-web \ --image=registry.access.redhat.com/ubi9/httpd-24:latest --replicas=3 --port=8080 [you@laptop ~]$ oc expose deployment/gateplan-web --port=8080 --target-port=8080 [you@laptop ~]$ oc expose service/gateplan-web

What you must deliver, in order:

  1. Establish which image is running, by digest, and record it somewhere you can find again.
  2. Make the application safe to update: whatever chapter 11 says is missing, add it.
  3. Configure the strategy so that capacity never drops below three pods at any moment during an update.
  4. Start a measurement loop against the route, and keep the output.
  5. Update to registry.access.redhat.com/ubi8/httpd-24:latest with a recorded change cause.
  6. Report the number of non-200 responses observed. If it is not zero, say why, and fix it before continuing.
  7. The team reports a problem. Roll back to the previous version in a single command, and prove the running image is the one from step 1.
  8. Explain, in two sentences, what you would have to change to make step 7 reliable if the deployment had referenced :latest throughout.
*
Tip

Step 6 is the one that catches people. If you see any 503, the usual causes are: no readiness probe, maxUnavailable greater than zero, or a probe whose period is so long that a pod is declared ready before it can serve.

?
Check

Zero failed requests during the update, a rollback that took one command and a few seconds, and a running image whose digest matches what you recorded in step 1. Then clean up: oc delete project ${U}-gateplan2.

12.11 Watch out, and summary

Watch out

TrapWhat is really happening
Deploying with :latestThe version changes on a reschedule or a scale-up, with no deployment and no trace.
Rolling back a floating tagThe pod template is restored; the image it names may have moved. Use a digest or an image stream.
A rolling update with no readiness probeOld pods are removed before new ones can serve. The update is the outage.
Expecting a failed rollout to undo itselfIt does not. The old pods keep serving and you must run oc rollout undo.
Three commands, three rolloutsUse oc rollout pause and resume to group them.
An empty CHANGE-CAUSE columnNobody annotated. The history becomes useless exactly when you need it.
Comparing crictl images IDs with registry digestsThe local IMAGE ID is a node-local identifier and has nothing to do with the registry digest.
oc create istag in a scriptCreate-only. It fails on the second run; use oc tag or oc import-image.
--scheduled plus automatic triggersOne upstream change redeploys every watching workload, unattended. Decide whether you want that.

Summary

  • A tag can be moved; only a digest cannot. Reproducibility comes from a digest, an image stream, or a tag you personally control.
  • imagePullPolicy defaults to Always for latest and IfNotPresent otherwise - which is why a moved tag sometimes takes effect and sometimes does not.
  • Every pod-template change starts a rollout; RollingUpdate replaces pods progressively, Recreate stops everything first.
  • maxSurge and maxUnavailable are yours to set, and maxUnavailable: 0 with a readiness probe is what gives an update with no failed requests.
  • Old ReplicaSets are kept so that oc rollout undo is a scale operation, not a redeployment.
  • A failed rollout is never undone automatically; it holds the old version and waits for you.
  • Image streams record digests and their history, so promoting and rolling back become moving one tag.
  • An image change trigger turns that tag move into a rollout - per container, and with a blast radius worth thinking about.

13.7 Cleaning up

Before you leave, remove your projects. The cluster is shared, and the next session starts on it.

Caution

Check what you keep first. Deleting a project deletes its persistent volume claims, and with a Delete reclaim policy that destroys the data. Everything you want to take home should already be a file in ~/do108/ on your own laptop - the cluster expires in any case.
