6.6 Lab 6.1 - Deploy the flight board from the console

Guided lab Lab 6.1 - First contact, from the console
Goal. Deploy the FIDS web front end from the web console, then find every object that was created for it. Time. 15 minutes. Prerequisites. Lab 0 completed; you are logged in.

  1. Open the console and log in with your userN account.

    [you@laptop ~]$ oc whoami --show-console

    If a guided tour offers itself, dismiss it with Skip tour.

  2. Switch to the Developer perspective using the switcher at the top of the sidebar, then create a project. Go to +Add, and use Create a new project. Name it userN-fids, using your own account number.

    !
    Caution

    Use your own prefix. Project names are unique across the whole cluster, and the person who takes fids takes it from everybody.

  3. Deploy the flight board. In +Add, choose Container images. Enter the image name below, leave the rest at its defaults, and click Create.

    Image to deploy
    registry.access.redhat.com/ubi9/httpd-24:latest

    Set the application name to fids and the component name to fids-web if the form offers those fields.

  4. Watch it start. The Topology page opens and shows one circle. It turns from light to dark as the pod moves from ContainerCreating to Running. Click it, and read the panel on the right: Resources lists the pod, the service and the route that were created for you.

  5. Open the application. Click the small arrow at the top right of the circle, or the route URL in the side panel. You should get the default page of the Apache HTTP Server container.

    i
    Note

    That default page is the deliverable for now. In chapter 10 you will replace its contents with the real flight board, without rebuilding the image.

  6. See the same thing as an administrator would. Switch to the Administrator perspective and visit, in order:

    • Workloads → Deployments - one fids-web deployment. Open it and look at the YAML tab: this is the object you will be writing by hand from chapter 9 onwards.
    • Workloads → Pods - one pod, whose name is the deployment name plus two random suffixes. Open it: Logs, Events, Terminal, YAML.
    • Networking → Services - one service, with a ClusterIP address that no browser on your laptop can reach.
    • Networking → Routes - one route, with the hostname that your browser can reach.

  7. Cross-check from the CLI. Both interfaces read the same API:

    [you@laptop ~]$ oc project ${U}-fids [you@laptop ~]$ oc get deployment,pod,service,route NAME READY UP-TO-DATE AVAILABLE AGE deployment.apps/fids-web 1/1 1 1 3m NAME READY STATUS RESTARTS AGE pod/fids-web-6b9c7d5f4c-2xk9p 1/1 Running 0 3m NAME TYPE CLUSTER-IP PORT(S) AGE service/fids-web ClusterIP 172.30.41.207 8080/TCP 3m NAME HOST/PORT SERVICES route.route.openshift.io/fids-web fids-web-user1-fids.apps.cluster-... fids-web

  8. Note two facts in your notebook - you will need them all week: the node your pod landed on, and the route domain of this cluster.

    [you@laptop ~]$ oc get pod -o wide [you@laptop ~]$ oc get route fids-web -o jsonpath='{.spec.host}{"\n"}'
?
Check

The lab is complete when: the route answers in a browser; oc get deployment,pod,service,route lists exactly four objects; and you can say, out loud, what each of the four is for. Keep the project - the next lab uses it.
